# Bulava: notes for Claude Code

The master product and engineering specification was provided in the first session. The architecture it produced is in `docs/architecture.md`. Read that file and `docs/decisions.md` before changing anything structural.

## Rules

- Event platform first. Never hard-code wedding assumptions, event types, pricing, translations or template layouts. Categories, languages, plans and templates are DB rows or catalog data.
- EVENT, FUNCTION, AUDIENCE and ACCESS POLICY stay separate models. Guest visibility is decided only by `evaluateFunctionAccess` in `packages/auth`.
- Tenant routes are nested under `/api/v1/events/:eventId/...` and decorated with `@RequireEventPermission(...)`. Services must scope every query by `access.eventId`. Never take tenant ids from the request body. Staff routes use `@RequirePlatformPermission(...)`.
- Validate input with shared Zod schemas from `@bulava/validation` (`@ZodBody(Schema)`).
- Throw `AppError('<CODE>', message)`. Add new codes to `ErrorCode` and an `error.<CODE>` key to the English catalog (and Hindi for guest-facing codes).
- UI strings use `t('key')`. Web keys live in `packages/localization/src/catalogs/` (Hindi for guest-facing strings); admin console keys live in `apps/admin/src/lib/i18n.ts`.
- Templates are data. New visual features (sections, openings, ornaments, hero variants) go into `packages/template-engine` and the schema enums, then templates select them in `templates/src`. Run the catalog tests: every template must pass the check matrix.
- The sections below a hero are dressed by the theme's suite (`theme.ornament`, single pieces swapped by `theme.dress`; ADR-069, docs/templates.md#section-suites): a new section layout or piece goes into the engine's sections and suites and its schema enum, never per-template CSS. Template sections render as server components: pass the dress as a prop, never React context or state in the engine. Two templates of one occasion never share a hero (`heroSimilarity` below `HERO_LOOKALIKE`) or a lower page; retired lookalikes are listed in `templates/src/lookalikes.ts`.
- A template's tradition is `theme.faith`, set centrally by `withFaith` (`templates/src/faith.ts`) from its tags, never by hand (ADR-070). Faith templates of the emblem occasions wear their faith's emblem at the very top (upright, one size, never touching words, never at the foot); sample people and photos follow the tradition, and the parents' line follows `mothersFirst` (the mother first on Hindu, Sikh and no-faith designs). Sample photos are static files credited in `samples/CREDITS.md` (CC0, public domain, or a library's licence through its API), never data URIs or web image search results.
- Template tiers are `FREE`, `PREMIUM` and `SIGNATURE` (ADR-067; `templates.maxTier` 0, 1 and 2: Premium comes with any paid plan, Signature from the Premium plan). Plan keys (`STARTER`, `STANDARD`, `PREMIUM`, `ULTIMATE`) are a different thing: never rename one for the other.
- Commissioned paintings are `artworks` in the definition: full-canvas transparent layers (licensed image assets, each listed in `assets`) that become the same `SceneArt` as drawn scenes. Browsers load them only through `/api/v1/public/template-assets/:id`; never hand out raw storage keys. The artist brief is docs/illustration-brief.md.
- Illustrated scenes (`template-engine/src/art`) are shared by website heroes, films and posters: draw on the 1200×800 canvas with the story inside x 415–785 (what every phone shows), text in the top ~55% and art in the bottom ~45%, position with inline styles (no Tailwind inside scene layers), use `rand()`/`r2()` instead of `Math.random`/raw trig (hydration), and never build JSX at module load (Remotion defines `React` late). A new font family needs a loader in `apps/video-worker/remotion/fonts.ts`. Render film stills to check a change (see docs/templates.md).
- Canvas sections (`section: 'canvas'`) are free-form artboards edited in the console's Design Studio (docs/templates.md#canvas-sections). Keep their rendering CSS-only (percentage positions, `cqw` sizes, container queries; only `FitText` measures in the browser). A new layer kind, widget or ornament goes into `packages/template-schema/src/canvas.ts` and `packages/template-engine/src/canvas/`, then into the Design Studio's presets, Elements panel (with its search words) and inspector. Canvas images are licensed assets listed in `definition.assets` (role `canvas`) or host-photo bindings, never raw URLs.
- The console's Design Studio (ADR-075, `apps/admin/src/components/canvas-editor/`) edits every board of a template as pages (`pages.ts`: canvas sections, film and card scenes): a new staff tool goes there for websites, films and cards alike, and multi-select stays in the shared `Stage` behind optional props. Imports (`canvas-editor/import/`, `readDesign`) read designers' files in the browser and send nothing until they are placed: clean an SVG before it touches the DOM, never upload SVG or data URIs as assets, and every picture an import makes goes through the licensed upload (`uploadToStorage`, `POST /admin/assets` with a licence).
- Canvas illustrations (`template-engine/src/art/illustrations-*.tsx`) follow the scene rules and take their colours from the layer's tint and the palette (fixed colours only for real flowers, leaves and flames: `NATURE`). Build curves with the helpers in `art/kit.tsx` (`taper`, `onCubic`, `frameAt`), not trigonometry. A new illustration goes into `ILLUSTRATIONS`, the component map and `ILLUSTRATION_ASPECT`; check it in the editor's add menu and on a card render.
- Marketing and dashboard UI follow docs/web-design.md: the clay surface classes (`clay`, `clay-inset`, `btn-3d*`, `icon-3d`) instead of one-off shadows, lucide icons (no emoji), `data-header-tone` on every full-width marketing section, CSS entrances above the fold and `Reveal` below it, every effect off for reduced motion, and no inputs or selects in the dashboard shell. Keep the marketing pages fast (web-design.md "Speed"): the hero headline is never hidden at first paint, trackers load on first interaction, and code shared by every page never imports a package entry point that pulls in the template engine.
- New catalog invitations are themes in `templates/src/factory/` (a kit of art, an occasion, layouts over the shared compositions; docs/templates.md#template-factory), not hand-placed canvases. Two templates of one occasion never share a look (`designLook`: the same art in another colourway belongs in the presets), and galleries show each look once (`onePerLook`; docs/templates.md#lookalikes). Public template lists carry no definitions: fetch one per key, or `keys=` with `include=definition` (at most 60).
- Hosts design every website and every film on the canvas (ADR-057, ADR-059 to ADR-061): their artboards (`customization.canvas`), the sections they add or redraw (`addedSections`, `replaces` for a template section drawn in its place by `sectionBoard`), their redrawn and added film scenes (`scenes`, `addedScenes`) and the film's size (`filmFormat`) are drawn only while they fit and are validated with the template (`validateCustomization`): never let a host's button link anywhere but the event's own details, or an image read anything but a photo binding. The website and film editors are one `BoardStudio`; the card editor shares its stage, inspector and panels through `BoardEditorApi`. New editor tools go there, not into one editor. Editors are light or dark: `editor-chrome` on everything around the canvas, `--ed-*` variables instead of fixed colours (docs/web-design.md#editors). The website editor draws the whole page in one flow (ADR-065): `TemplateRenderer` `wrapSection` inside a `FrameDocument` of the phone's or desktop's width, the host's order in `sectionOrder`. Template sections answer to container queries (`@min-[640px]:`), never viewport breakpoints (`sm:`), and screen-high sizes read `--bulava-screen`. Clicking a template section makes it a stand-in whose board keeps the template's own section behind (a `section` layer, by id, only in a redrawn section for the section it stands in for) with its words measured from the page as text layers (`components/design/section-snapshot.ts`).
- Openings the guest pulls open (`zipper`, `ribbon`; ADR-074) are drawn in `template-engine/src/covers.tsx` in the template's palette, follow the finger and open on a tap or a key too; a film scene opens under the same cover with `scene.reveal`, never a video of one.
- Films can film canvas artboards (`scene.canvas`, ADR-058): drive their motion from the frame number (`layerStyle`), never CSS animations. Canvas films come from `templates/src/canvas-films.ts`.
- The design page (`/design`, ADR-063) is for everyone: websites and films designed there before signing in are drafts on the visitor's device only (`lib/design-drafts.ts`), never server rows, and reach an event through the new-event flow (`?studio=`) after signing in; publishing a design beyond the free plan's, making the video and downloading a watermark-free card ask for a plan (the free plan publishes one free design with the site's address across it, ADR-067). The blank canvas (`blank-canvas`, its film `blank-canvas-film`) is a catalog template tagged `blank`: galleries, the sitemap and the home page leave it out (`isBlankTemplate`).
- Stock images come only from licensed libraries (Pexels, Pixabay; the `stock` settings group, ADR-064), never a web image search. The browser sends a library and an id, never an address; the server asks the library's API for the file, downloads it only from the library's servers within `StockService`'s budget, checks the bytes, and stores it like an upload (design photos, card photos).
- Likes are real (ADR-055): one per account or browser, counted with the row, shown only when the `likes` settings allow; never seed, inflate or edit `likeCount`.
- Digital cards (docs/cards.md) are canvas templates' opening artboards turned into `CardDesign`s by `cardFromTemplate`; draw a card only with `CardView` (editor, previews and the export renderer must match), keep its tokens in headers or after a `#` (never in a path or query string), and record conversions (downloads, payments, emails) on the server, never from a click. A paid order freezes its design and is the entitlement: retries, emails and re-renders never charge again. A free card carries the site's address across it and a band along its foot and saves as a PNG or a JPEG; a PDF comes only with a watermark-free card (`CARD_PDF_LOCKED`, enforced by the API), and plans include watermark-free cards by design (`cards.included`, ADR-071).
- Venue search goes through the API (`/events/:eventId/places`, `function.manage`) with the server's Places key (a secret in the `maps` settings), never a key in the browser; a pasted map link is resolved only within Google's hosts (ADR-072). A new event starts with its occasion's main function, and functions take a start only.
- Galleries show pre-rendered template previews (`apps/web/public/template-previews/` + `src/lib/template-previews.json`). After adding or changing a template, run `node infrastructure/scripts/template-previews.mjs` against a web app started with `TEMPLATE_PREVIEW_FRAMES=1` and commit the images and the manifest (docs/templates.md#marketing-previews).
- The home page's template sections and the card gallery's Featured order read the console's picks first (`showcase_sections`, `showcase.manage`, `GET /public/showcase`) and fill the rest automatically (`withPicks`); a new home section that shows templates gets a showcase section (`SHOWCASE_SECTIONS`), never hard-coded keys.
- Template text uses the contrast-corrected ink variables (`--t-text`, `--t-*-ink`, `--t-on-*`), never raw palette colours; `pnpm a11y` must report no serious issues.
- Pages that show account, guest or event data are listed in `apps/web/src/lib/private-routes.ts` and render per request (`export const dynamic = 'force-dynamic'`), so they get the nonce CSP. Never add inline `<script>` tags; third-party scripts load from client effects on marketing pages only.
- Guest-facing links (invitations, album QR codes) get their origin from `EventLinksService.guestOrigin(eventId)` (custom domains), never from `WEB_ORIGIN` directly.
- Redirect targets read from a link or a form (`?next=`, the Google flow's `next`) go through `safeRelativePath` (`@bulava/validation`); never check them by hand with `startsWith('/')`.
- Write security-relevant changes to the audit log (`AuditService.record`, pass `tx` inside transactions).
- Object storage is private: serve files only through signed URLs issued after an authorization check, and verify uploads server-side.
- The album link and its QR codes open the gallery (public with downloads by default); they never upload on their own. Photos come from the team (`media.upload`, dashboard) or from invited guests carrying their invitation token when the host allows guest uploads (`uploadsEnabled`). QR entry passes are opt-in (`Event.entryPasses`). A function without a date is a placeholder: templates, invitations and the public page never show it, and the setup step counts only functions with a date, time and venue (`counts.readyFunctions`).
- Schema changes go through Prisma migrations. Hand-written SQL (partial indexes, checks) goes at the end of the migration file. When `migrate dev` refuses to run non-interactively, generate SQL with `prisma migrate diff --script` into a new migration folder.
- Never run `prisma migrate reset` or truncate shared databases. The e2e suites are non-destructive by design.
- Never commit secrets. `.env` holds real credentials locally; test runs should point storage at local SeaweedFS, not the real R2 bucket.
- NestJS constructor parameter types must be value imports (no `import type`), or dependency injection breaks.
- Never derive an update schema with `.partial()` from a schema that has `.default()`s: Zod 4 fills in defaults inside partial objects and silently resets omitted fields. Build update schemas from default-free fields (see ADR-024).
- Functions exported from a `'use client'` module cannot be called in server components; put shared helpers in plain modules (e.g. `apps/web/src/lib/guest-view.ts`).
- Production shares a server with other sites (ADR-030): the stack publishes only `bulava-nginx` on `127.0.0.1:${BULAVA_HTTP_PORT}`, never 80/443 or `0.0.0.0`. Keep http-level Nginx settings inside `infrastructure/nginx/` (the host site in `nginx/host/` is one server block with no `default_server`), host names come from `.env.production`, and CPU limits must stay settings (a limit above the host's CPU count stops the container).
- The dashboard creates events as one private link and asks who can open the invitation only when publishing (the publish dialog, `PublishProvider`); never add an access question to creation. The setup steps live in `apps/web/src/lib/setup-steps.ts` and feed the overview checklist, the sidebar ticks, the home page and the next-step bar; add a step there, not in a page.
- Accounts made by the quick start are *provisional* (`User.provisional`): they may design, preview and edit, never publish, pay, invite guests or add team members until secured (`assertVerifiedAccount` → `ACCOUNT_UNVERIFIED`). Template tiers, the number of events (`events.max`, published events only; 1 on the free plan, which publishes one event with one function on a free design, with the site's address across it, and no replies or gallery: ADR-067), the functions with a date and the guests are enforced when an event is published (any status change out of `DRAFT`: guests can open every non-draft event), never when a draft is created or saves a design (ADR-054, ADR-062). Preview links are `Event.previewToken` (`/preview/<token>`, always watermarked, never indexed) and end at publishing (the API then returns only the slug and the web redirects to `/e/:slug`); never add a `?preview` flag to `/e/:slug`, and show the public link only once published. WhatsApp sign-in codes go through the `whatsapp` queue as an approved template; never put a code in a database row or a response.
- An email joins an account only after a code proves it (ADR-045): email codes, adding an email and password resets go through `EmailCodeService` (codes live in Redis under the challenge token's hash, never in a row or a response). Signing in is one form (`/login`, ADR-052): an email or a WhatsApp number, or Google; the form makes an account only on its last step (a name, the unticked Terms box, an optional password) after a code or Google proved the address or number, and every other sign-up (quick start, team invitation) also takes the unticked box and leaves the password optional. A password may sign in by itself, but never instead of the authenticator app, and ten wrong ones pause it. WhatsApp codes sign in only to an account whose number is confirmed (or the provisional account made from it); any new way in keeps these rules.
- Plans and add-ons are one-time purchases that belong to the account, bought on the checkout page (`/dashboard/checkout`, `POST /orders`; ADR-052, ADR-053, ADR-062): plan cards only choose, nothing asks for an event, prices and coupons come from `POST /orders/quote`, the purchase terms are ticked there, and signing in from a plan returns to it (`/login?next=`). Plans and add-ons are `pricing_plans` rows (`kind`, `visibility`, `offeredTo`, `stackable`); never hard-code a price. A bigger plan is paid for the difference (`creditMinor`), add-ons add to the plan (`withAddOns`), a hidden plan is sold only through a signed offer (`POST /orders/offers`), and only the owner buys (`billing.manage`). Nothing renews: Razorpay Orders only, never subscriptions. Customer copy says "unlock", never "upgrade", and names one-time payment and GST; a plan limit names the limit and links to unlocking it (`lib/plan-limits.ts`). The plan an event runs on (`GET /events/:id/plan`, ADR-066) is the bigger of the owner's account plan and one bought or given for that event alone; show plans by their names from it, never from the template tier. An add-on bought from an event (`eventId`) goes with that event when the event's own plan is the bigger; the console's grants are the account's unless an event is chosen. Functions and guests are limited only on published events (drafts hold any number; publishing checks them).
- Staff routes require two-step sign-in in production (`STAFF_MFA_REQUIRED`). Guest logistics and seating never grant access; reminders are sent only by the worker.
- Site pages (About, Contact, the policies, pages staff add) are rows in `site_pages`, edited in the console (Pages, `page.manage`) and seeded once from `packages/database/src/site-pages.ts`; never hard-code legal or company text in the web app. Company details reach the pages as placeholders (`{legalName}`, `{address}`, `{grievanceOfficer}`, `{supportEmail}`) from the settings. Contact-form messages are answered from the console inbox (`contact.manage`), and checkouts always end on `/dashboard/payments/:orderId`.
- Consent is an unticked box the person ticks (sign-up, Google sign-up, every purchase), validated with `acceptTerms` and recorded through `ConsentService` with the policy versions; never pre-tick or infer it. Account deletion goes through `AccountService` (30-day `PENDING_DELETION` restore window, then the worker erases); never anonymize an account directly.
- Site settings and integrations (branding, SEO, trackers, custom code, Razorpay, SMTP, WhatsApp, Google sign-in, Maps, custom domains) are rows in `platform_settings`, edited only by the Super Admin (ADR-033). Read them through `SettingsStore` / `PlatformSettingsService`, never `process.env`; a new group or field goes into `packages/validation/src/settings.ts`, its secrets into `SETTING_SECRETS` (encrypted, write-only, never returned or logged), and an old environment variable into `envFallback`. `GET /public/site-config` must never carry a secret. Storage stays in the environment.
- There is exactly one Super Admin (a database index). Never assign `SUPER_ADMIN`: it is handed over (`/admin/staff/transfer-super-admin`) or moved with `pnpm admin:set-role <email> SUPER_ADMIN --replace`. Give new staff features their own platform permission in `packages/auth/src/permissions.ts` (Super-Admin-only ones go in `SUPER_ONLY`), and mirror it in the console's `PlatformPermission` type and `perm.*` labels.
- WhatsApp messages count against the plan's `messaging.whatsapp.max`. Anything that queues WhatsApp notifications calls `lockWhatsAppAllowance(tx, eventId)` inside its transaction before counting what is left.
- Follow-ups go through `MessagesService` (ADR-073): `toGuests` (email to guests with an address, WhatsApp within the allowance to numbers that reach it) and `toBuyer` (the buyer's confirmed number; buyers' rows carry no event, so they never touch an allowance). Each WhatsApp kind is an approved template in `WHATSAPP_TEMPLATE_KINDS`, with its variable count in `WHATSAPP_TEMPLATE_VARIABLES`, a console field and an `int.whatsapp.*` label; variables are never empty and never contain line breaks. Every WhatsApp send skips numbers that are unreachable or opted out (`whatsappNumbersToSkip`, `whatsapp_numbers`), a provider's "undeliverable" goes through `whatsappMessageFailed` (which fails the row, marks the number and writes the email fallback), and incoming messages go through `WhatsAppInboxService`. Bulava's number never answers guests by itself: their messages go to their host.
- WhatsApp is sent by the provider the settings choose (GetGabs by default, or Meta's Cloud API), both `WhatsAppProvider`s in `apps/worker/src/providers.ts` sending the same approved templates; readiness is `whatsappReady` (ADR-042). Delivery reports from any source go through `recordWhatsAppDelivery`, which only moves a delivery forward. GetGabs' reports are read back by the worker's `whatsapp-status` sweep, and its unsigned chats webhook is authenticated by the token in its query string (never in a path, which Nginx logs).
- E2e tests that need the Super Admin borrow the one seat and give it back, and restore any settings they change (see `super-admin.e2e-spec.ts`).
- Tests and browser checks are deliberately not committed (`.gitignore`): keep them in the working copy, run them before releases, and never `git add -f` them. CI runs lint, typecheck, builds and the security scans only.

## Commands

```bash
pnpm infra:up && pnpm build:packages   # after changing any package, rebuild it (apps consume dist/)
pnpm lint && pnpm typecheck && pnpm test && pnpm test:e2e
node infrastructure/scripts/ui-smoke.mjs --out <dir>          # needs web, api and workers running
ADMIN_EMAIL=… ADMIN_PASSWORD=… node infrastructure/scripts/admin-smoke.mjs --out <dir>
```

On Windows the shell tool can mangle quotes and collapse `\\` in heredocs. Write TS/TSX files with the file-writing tool, or generate strings with `chr(92)` in Python. Stopping a background dev server may leave its `node` child holding the port; stop that process id.
