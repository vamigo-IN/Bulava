## Security review (2026-10-11)

What was checked before the canvas release, and what changed:

- **SQL injection.** Every query goes through Prisma; the few raw statements are tagged templates (parameters, never spliced strings), and no `$queryRawUnsafe` exists. A live suite sends classic payloads (`' OR '1'='1`, `; DROP TABLE`, `pg_sleep`, `UNION SELECT`, operator objects) through query strings, paths and JSON bodies of public, auth and event routes: no server errors, no data in answers, nothing changed.
- **Floods and rate limits.** The live suite runs the real HTTP stack with rate limiting on: bursts of sign-in requests are cut at 10 a minute per client (other clients unaffected), any public route at 120, likes at 30, quick starts at 6. Client addresses come from Nginx, which replaces `X-Forwarded-For`, so a client cannot pose as another to escape its limit.
- **DDoS posture.** Nginx turns floods away cheaply (per-IP request, connection and sign-in limits, slow-client timeouts), bodies are capped (10 MB at the edge, 256 KB of JSON at the API), and expensive lists are cached in Redis. A single 1-vCPU server cannot absorb a volumetric attack by itself: once the domain is live, put Cloudflare in front (`cloudflare-real-ip.conf` is ready) with its DDoS protection, rate-limiting rules for `/api/v1/auth/` and Bot Fight Mode.
- **Requests the API must refuse**, all in the live suite: oversized (413) and malformed (400) bodies, cookie-authenticated changes without the CSRF header or from another origin, cross-origin preflights, another person's event (read, write, guests, design), forged or `alg: none` tokens, fields nobody may set on creation (status, owner, ids), path tricks on files; answers carry the security headers and never internals.
- **Found and fixed:** the `?next=` open redirect through a tab or newline (see `safeRelativePath`); image layers that could read a text slot as an address (now photo bindings only); oversized and unreadable bodies answered as server errors (the body parser's errors now come back as 413 `PAYLOAD_TOO_LARGE` and 400, without filling the error log); no CSP at all on APIs with Swagger switched on (staging, local), now the strict policy everywhere but the Swagger UI; Next.js 15.5.26's cache poisoning of SSG and ISR pages in self-hosted apps (GHSA-4jqv-mc3x-m676, GHSA-mcj8-r9mp-w47p), upgraded to 15.5.27. `pnpm audit --prod` reports no known vulnerabilities, and the secret scan of tracked files finds none.
- **Also reviewed:** server-side requests go only to fixed providers or hosts the Super Admin configures (no SSRF from user input); the only raw HTML is the JSON-LD block, with `<` escaped; `nginx -t` passes on the production image with the new limits.

## Known gaps (tracked)

- Pre-rendered marketing pages (home, templates, pricing, legal) keep a static CSP with `'unsafe-inline'` scripts, because a per-request nonce would force them to render on every request and give up caching. They hold no session data or personal information, and the CSP still limits where scripts load from. Every page that shows account, guest or event data uses the nonce policy.
- The session hint cookie `bulava_session` is readable by scripts. It carries no secret (only `1`); the session itself stays in httpOnly cookies.
- Remotion renders fetch fonts from Google Fonts at render time; self-hosting the font files would remove that outbound dependency.
- Admin console access is protected by role and session; adding an IP allowlist (commented in the admin server block of `templates/bulava.conf.template`) or Cloudflare Access in front of the admin host is recommended (`nginx.md`).
- Uploaded SVG design assets are only ever displayed with `<img>` (scripts do not run there), but they are not sanitized; keep asset uploads limited to trusted staff. The same holds for an SVG logo or favicon.
- Header and footer code saved in the console runs with full script rights on marketing pages (within the hosts the CSP allows). Only the Super Admin can save it; paste code only from trusted providers.
- Integration keys are encrypted with `TOKEN_ENCRYPTION_KEY`, like invitation links. Rotating that key means entering them again in the console.
- The legal pages (privacy, terms, refunds, shipping, cookies, account deletion, grievance redressal) are written for the DPDP Act and Rules, the IT Act with the SPDI and Intermediary Rules, and the Consumer Protection (E-Commerce) Rules, but still need review by counsel before launch (spec §84). Their company details (legal name, address, grievance officer) come from the settings and must be filled in.
- Users who signed up before consent was recorded have no consent rows; they are not asked again.
