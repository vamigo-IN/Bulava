# Architecture decisions

Short records of decisions that are costly to reverse.

### ADR-001: Stable major versions (2026-09-27)
We use TypeScript 5.9, NestJS 11, Prisma 6, Next.js 15, Zod 4, Tailwind 4, Jest 29 and Vitest 3. Newer majors exist (TypeScript 7, NestJS 12, Prisma 7/8, Next 16), but the previous majors have mature, proven interoperability. Upgrades are planned deliberately, one at a time.

### ADR-002: UUIDv7 primary keys
UUIDv7 ids are time-ordered, which is good for B-tree locality and cursor pagination, and non-sequential, so they are safe in URLs. There are no separate public ids.

### ADR-003: Separate models for event, function, audience and access policy
`AccessPolicy` is its own table, owned by an event (required) or a function (optional override). Audience is `FunctionAudienceGroup` plus `FunctionGuest`. Invitation scope is `Invitation.functionId`. This follows the spec's rule that the four concepts must never collapse into one permission field.

### ADR-004: One pure access evaluator
All guest-visibility decisions go through `evaluateFunctionAccess` in `packages/auth`. It has no I/O and is exhaustively unit tested. The host dashboard's access matrix uses the same function.

### ADR-005: GROUP_RESTRICTED is strict
Under `GROUP_RESTRICTED`, a direct `FunctionGuest` assignment is not sufficient; the guest must be in an audience group. Otherwise the mode would be indistinguishable from `INVITE_ONLY`. An explicit deny still applies.

### ADR-006: Invitation tokens are hashed and encrypted
Lookup uses SHA-256 of a 256-bit token. Hosts need to copy links repeatedly (WhatsApp sharing), so an AES-256-GCM ciphertext is also stored under `TOKEN_ENCRYPTION_KEY`. A database leak alone reveals no usable links. Rotating the key requires regenerating links.

### ADR-007: Tenant routes are nested under /events/:eventId
The spec lists flat routes (`/api/v1/guests`). We nest them (`/api/v1/events/:eventId/guests`) so the tenant id always comes from the path and one guard enforces membership before any handler runs.

### ADR-008: Web proxies the API on the same origin
`/api/v1/*` on the web origin is rewritten to the API. Auth cookies are first-party and httpOnly, CSRF protection is simple, and guests never need cross-origin requests. The API keeps CORS for the admin app and other clients.

### ADR-009: Custom header CSRF instead of double-submit tokens
All mutations need `X-Bulava-CSRF: 1`, together with SameSite=Lax cookies and an Origin allowlist. It is simpler than synchronizer tokens and equally strong while the API's CORS allowlist stays strict.

### ADR-010: Invitation opens and link previews
Each API view increments the token's use count, which is what enforces single-use links. The web page therefore answers known link-preview bots (WhatsApp, Facebook, Telegram and others) with a generic page and never calls the API for them.

### ADR-011: Event categories, languages and plans are data
They are stored in `event_types`, `languages` and `pricing_plans` / `plan_features`, and seeded idempotently. Admins change them without a deploy, and category-specific details are validated by `Event.details` schemas keyed by `detailsSchemaKey`.

### ADR-012: Non-destructive e2e tests
Prisma blocks `migrate reset` when run by AI agents, and resetting shared databases is risky anyway. The e2e suite uses `migrate deploy` and unique data per run instead of wiping.

### ADR-013: SeaweedFS for local object storage
The MinIO image was unavailable from both registries during development, so the local S3 stand-in is SeaweedFS. Code only speaks the S3 API through `@bulava/storage`, so production uses Cloudflare R2 unchanged.

### ADR-014: A separate admin app on its own domain
The staff console is `apps/admin` on `admin.bulava.in`, proxying `/api/v1` like the web app. Staff and customer sessions never share cookies, the console can be put behind an IP allowlist or Cloudflare Access independently, and customer bundles carry no admin code. `/users/me` exposes platform permissions as a UI hint; enforcement stays in `PlatformPermissionGuard`.

### ADR-015: Openings, motifs and music live in the engine, not in templates
Signature openings (lanterns, gates, seal, petals, celestial, scratch), hero variants and ornaments are engine features that templates select by name. Templates stay pure data, every template can use every feature, and all of them are covered by the same tests. Music starts only on the opening's user gesture, because browsers block autoplay.

### ADR-016: Prebuilt Remotion bundle in the video image
Bundling the Remotion project needs webpack and the TypeScript sources of workspace packages. The image bundles once at build time and the worker serves that folder, so production containers start instantly and carry no sources.

### ADR-017: Registrations create real guests with invitations
A confirmed registrant becomes an ordinary guest with an event-wide invitation, instead of a parallel "attendee" model. RSVP, galleries, announcements and check-in work unchanged, and access is still decided by `evaluateFunctionAccess`. Capacity is enforced under a row lock on the event's registration settings.

### ADR-018: Scheduled lifecycle and retention in the general worker
Completing, archiving and purging events are repeatable BullMQ jobs, not cron on the host, so they run once across replicas. Purges delete storage first and keep orders, entitlements and audit rows (plain `eventId` columns).

### ADR-019: Lint once at the root
`eslint.config.mjs` lints the whole monorepo with the TypeScript, React Hooks and Next.js plugins. Next's per-app lint during `next build` is disabled to avoid a second, differently configured pass. `consistent-type-imports` is deliberately off: NestJS dependency injection needs constructor parameter types as runtime values.


### ADR-020: Two-step sign-in with TOTP, required for staff
Authenticator-app codes (RFC 6238) and one-time recovery codes, implemented in `packages/auth` without new dependencies. Password sign-in for such accounts yields only a short-lived challenge, never a session; the session row and access token record that the second factor passed, and `PlatformPermissionGuard` requires it for staff when `STAFF_MFA_REQUIRED` is on (always in production). Codes are replay-proof through a stored last step claimed with a conditional update. Lost devices are reset by an operator CLI, not by support staff in the UI.

### ADR-021: Seating and logistics are not access
Tables live in `SeatAssignment`, not in `FunctionGuest`, because a `FunctionGuest` row is a direct assignment that grants entry. Seating a guest can never change who may attend, and guests only see seats for functions `evaluateFunctionAccess` shows them. Stays and travel are per guest, shown only to that guest, and deleted with the guest.

### ADR-022: Live photo walls use secret, rotatable links
A venue screen has no account and no invitation, so each album's wall has its own 256-bit link (hash for lookup, ciphertext for re-display), opt-in, rotatable and closed with the event. The wall exposes only approved, shareable images through short-lived signed URLs, and the client keeps each image's first URL so polling does not re-download photos.

### ADR-023: Reminders are dispatched only by the worker
The API stores reminder schedules; a per-minute repeatable job claims each due reminder with a conditional update and creates its notification rows in the same transaction, then re-queues any rows left `QUEUED`. Audience fact loading moved to `@bulava/database` so the worker and the API evaluate access identically. Delivery re-checks the situation (replied, moved, cancelled) and skips instead of sending stale reminders.

### ADR-024: Update schemas are built without defaults
Zod 4 applies `.default()` values even inside `.partial()`, so a partial PATCH built from a create schema silently reset omitted fields (album moderation and download settings, RSVP question options and scope). Update schemas are now derived from default-free field sets, with a regression test.

### ADR-025: Server-side template filtering, lighter previews and blocking metadata
Gallery previews are live markup, and the App Router ships every server-rendered element twice (HTML and the RSC payload). Passing all cards to a client-side filter made the gallery 1–1.5 MB and the homepage 1.8 MB. Filters are now links resolved on the server, the gallery pages at 24 cards, previews render two sections, and the template animation styles are one hoisted `<style>` per page instead of one per thumbnail: the homepage is 0.9 MB (91 KB gzipped) and the gallery 0.4 MB (85 KB). Separately, streamed metadata raced with hydration under CPU load (React #418 on dynamic pages, reproduced with a CPU-saturation replay); metadata is rendered in `<head>` (`htmlLimitedBots: /.*/`).

### ADR-026: Templates choose colours; the engine guarantees readable text
Template palettes are designer data, and many pair light accents with light backgrounds. `themeStyle` keeps the palette for decoration and publishes contrast-corrected "ink" variables for text (`--t-primary-ink`, `--t-accent-ink`, `--t-muted-ink`, `--t-on-primary` and so on), computed with `ensureContrast` so each reaches WCAG AA (4.5:1) on every background it can sit on. Engine sections use the ink variables for text, so every current and future template passes without hand-tuning, and the check runs in axe over all previews and openings. Opening labels breathe with a scale animation instead of fading, because opacity animation drops contrast mid-cycle.

### ADR-027: Google sign-in never merges into unverified accounts
Google sign-in (OIDC code flow with PKCE, verified with `jose`) keys accounts by the Google subject. Bulava does not verify email addresses at sign-up, so an existing account with the same email is linked automatically only if its email is verified; otherwise the owner links Google while signed in. Auto-merging would let anyone who registered someone else's address first take over that person's Google sign-in. The flow's state is single use in Redis and bound to the starting browser by an httpOnly cookie, and two-step sign-in still applies after Google.

### ADR-028: Nonce CSP for private pages, static CSP for marketing
A nonce requires rendering per request, and the marketing pages are pre-rendered and cached. Middleware therefore applies a nonce policy with `'strict-dynamic'` to every route that handles accounts, guests or event data (`lib/private-routes.ts`, rendered with `force-dynamic`), and to the whole admin console. Pre-rendered marketing pages keep the static policy with `'unsafe-inline'`. Policies are built once in `next.config.ts` and handed to the middleware through build-time `env`, so there is a single source. Third-party analytics load from a client effect, never inline, and never on private pages.

### ADR-029: Custom domains are aliases, proven by DNS, with certificates from Cloudflare for SaaS
A customer domain is an alias for one event: the web middleware maps its host to the event slug through a cached API lookup, serves the event page at `/` plus guest links, and redirects everything else to the main site. There are no per-domain Nginx blocks; the default server accepts any host, and certificates come from Cloudflare for SaaS (custom hostnames) behind a single fallback origin. Ownership is proven with a TXT record. Claims are not unique until verified (a partial unique index), so nobody can squat a name, and a lapsed verified claim gives way to a newer proof. `EventLinksService` is the one place that decides a guest link's origin, and it also feeds the CSRF allowlist. Active domains are re-checked daily and switched off after three failures, so a domain that changes hands cannot keep serving an event.

### ADR-030: Bulava shares a server behind its existing Nginx
The first target server already runs several sites: its Nginx owns ports 80 and 443, certbot manages every certificate, and other Compose projects publish their own ports. Bulava therefore no longer terminates TLS or publishes 80/443. `bulava-nginx` became an internal router, published only on `127.0.0.1:${BULAVA_HTTP_PORT}`, with host names rendered from `.env.production` by the image's envsubst. The server's Nginx gets one generated site file: a single server block, no http-level names and no `default_server`, so it cannot collide with other sites. Certbot handles TLS the same way as for the rest of the server. Real client IPs cross the loopback hop in `X-Real-IP`, which is trusted only from loopback and Docker ranges. CPU and memory limits became settings, because a CPU limit above the host's count stops a container from starting. Video rendering became an opt-in Compose profile, because it can saturate a small shared machine. The same layout works on a dedicated server; Cloudflare stays optional.

### ADR-031: Illustrated scenes are shared data; looks restyle sections; lookalikes are soft-deleted
Premium invitations in this market are illustrated and layered (temples, palaces, torans), and customers compare them with hand-painted video invites. We draw the art in code instead of shipping bitmaps: no image licences to track, every colour change recolours the art, and pages stay light. Each scene is data (`sceneArt`: a background and layers with a depth), laid out on one 1200×800 canvas with inline styles, so the same artwork is a parallax website hero, a Remotion film backdrop with a camera move, and a catalogue poster. Film text is fitted by measuring the real font in the renderer's browser rather than estimating, because estimates clipped long capitalised titles. Section appearance comes from a template-level `look` (bands, frames, card styles) rather than new section code, so one set of sections serves heritage, noir, royal, garden and celebration designs. Hosts get more freedom through capabilities, not new templates: named photo spots, font pairings, free colours on top of presets, openings, effects and hidden sections, all validated against the template and against the event's approved photos. Templates that looked alike were retired with a `deletedAt` soft delete (catalog list or admin action) instead of deletion, so events that picked one keep their pinned version.

### ADR-032: Commissioned paintings are layered assets on the scene canvas
Code-drawn scenes cannot match hand-painted art, so templates can also use commissioned paintings. Rather than a second rendering path, a painting is delivered as full-canvas transparent layers on the same 3:2 canvas as the drawn scenes and becomes the same `SceneArt` (one SVG `<image>` per layer), so parallax heroes, film camera moves, phone framing and posters needed no new code. The layers are licensed assets listed in the definition's `assets`, which keeps the existing licence gate at publishing. Storage stays private: a public route redirects to a short-lived signed URL only for approved, currently licensed images used by a published template version, signed at the top of the hour so browsers can cache it. Versions keep serving after a template is unpublished or deleted, because events stay pinned to them. The media worker makes 1200 and 2400 px WebP renditions (a phone shows only the middle third of the canvas, so heroes need the larger one) and never alters the licensed original. Films wait for every layer to decode before capturing a frame. Artwork lives in each definition, not a shared library, so published versions stay immutable; it moves between templates by duplicating a template or through the Studio's JSON tab. Painted art does not follow palette changes; a second colourway is a second layer set.

### ADR-033: The Super Admin runs the site from the console; one Super Admin, staff roles by area (2026-09-29)
The owner needed to change branding, SEO, trackers and integrations without a deploy, and to give staff narrower access than "platform admin". Site settings and integrations moved from environment variables into `platform_settings`, one row per group (site, SEO, tracking, code, payments, email, WhatsApp, maps, domains), edited only with `settings.manage`. Each group has a Zod schema and is saved whole; its keys and passwords sit beside the values, AES-256-GCM encrypted under `TOKEN_ENCRYPTION_KEY`, write-only (the console sees "set" and the last four characters) and never logged. A group that was never saved falls back to the old environment variables, so running deployments keep working, and its first save copies them over. The API and workers read settings through `SettingsStore` with a 15-second cache, so changes apply without restarts; workers rebuild a provider only when its settings change. Storage stays in the environment: every service must agree on the bucket, and moving it from a form would orphan existing files, so the console only shows and tests it. Public pages read a secret-free `GET /public/site-config`; trackers and header/footer code load from a client effect on marketing pages only, never on private pages (which keep their nonce CSP), and the marketing CSP gains exactly the hosts they need, as plain `https://host` sources. Staff access became six roles by area (support, content, finance, platform admin, Super Admin, plus customers), still enforced per permission. There is exactly one Super Admin: a partial unique index enforces it whatever the code does; the role is handed over with the owner's password and two-step code instead of being assigned; the seed only fills an empty seat, so deploys never take it back; and the CLI can move it for recovery. Complimentary upgrades are zero-amount `ADMIN_GRANT` orders that grant entitlements through the purchase code path, so payment history, access checks and revocation need nothing new; they cannot be refunded and are left out of revenue. WhatsApp Business sends approved templates through Meta's Cloud API from the worker. Each plan has a per-event message allowance, and host sends and scheduled reminders count it under one transaction-scoped advisory lock per event, so concurrent sends cannot overspend it; permanent Meta errors are recorded as failed and are not charged.

### ADR-034: Marketing motion is CSS above the fold and GSAP below it; no WebGL (2026-09-30)
The first homepage hero drew a three.js particle field and an aurora canvas behind the phones. They showed as a hard-edged panel on the dark background, cost a WebGL context and the three.js bundle, and animated only after hydration, so the phones appeared, vanished and animated in again. The redesign ([web-design.md](web-design.md)) lights dark sections with CSS radial gradients and film grain instead, and removes three.js and react-three. Anything visible on arrival (hero words, phones, status chips) animates with CSS keyframes that play from the first paint; sections further down reveal once with GSAP ScrollTrigger, which never runs before the visitor scrolls there. 3D is CSS perspective (the hero rig, template cards that lean toward the pointer), which composes with live HTML invitations. Lenis smooth scrolling stays on marketing pages only, never in the dashboard or on guest pages, where panels and forms scroll on their own. Every effect is off for reduced motion. Sections declare `data-header-tone` so the adaptive header needs no per-page code.

### ADR-035: Link modes share one link and take registrations by default; secret links expire (2026-10-01)
Hosts of public and private events expected to publish and then share a link on WhatsApp, but the only links Bulava produced were personal invitations, so they had to add guests one by one even when they wanted anyone with the link to come. The access modes now split into link modes (`PUBLIC`, `PRIVATE_LINK`, `SECRET_TOKEN`), shared with one link shown on the overview and the Invitations page, and personal modes (`INVITE_ONLY`, `GROUP_RESTRICTED`), which still need guests and invitations. Link modes take registrations by default, so the link alone fills the guest list; the default is applied when an event becomes link-shared and when a link-shared event has never saved a setting, never over a host's later "off". `SECRET_TOKEN` used to mean "invite only" in practice; it is now what its name says: the page opens only with a secret key in the link. The key is 256 random bits, stored as a SHA-256 hash and AES-GCM ciphertext so the host can copy it again, and it expires (a week after the event by default, at most a year ahead) and can be replaced, which a printed or forwarded link otherwise never could be. Keys in URLs leak through history and `Referer`, so the web middleware moves the key into an httpOnly per-event cookie and redirects to the clean address; the API accepts it from that cookie or a header. Guest visibility is still decided only by `evaluateFunctionAccess`, which learned the verified-link viewer.

### ADR-036: Team members are invited by email with a one-use code (2026-10-01)
Adding a team member required them to have a Bulava account first, which made hosts ask photographers to sign up before they could be added. Now an email without an account gets an invitation: a link and a 6-digit code. The person opens the link, enters the code, then chooses a name and password, and joins signed in, with the email marked verified because receiving the code proved it. The code has no time limit, as requested, because photographers are often booked weeks ahead; instead it works once, and five wrong codes lock the invitation until the host sends a new one, which bounds guessing at five tries per invitation against a million codes. Link and code are separate secrets (a 256-bit token for the link, the code for the person), both stored only as hashes. The code is an HMAC under a server key and bound to the invitation, like guest OTP codes, because a plain hash of six digits would fall to a million guesses from a copy of the database. The email job is removed from the queue once sent. If the email gains an account in the meantime, the person signs in and joins with the code, and only as that email. The dashboard now follows the role: the API returns the member's permissions with the event, the web hides sections and actions the role cannot use, sends photographers straight to Photos, and explains a section outside the role instead of showing a generic error. The API still enforces every permission.

### ADR-037: One album per event, with a folder per function (2026-10-01)
Hosts created several albums with different links and QR codes, and guests and photographers did not know which to use. Every event now has exactly one album (a partial unique index on `media_rooms.is_main`): one upload link and QR code, one gallery, one live wall. Photos are organised in sub-albums (`MediaAlbum`): one per function, created and renamed with the function, a General one, and any the host adds. Uploaders pick a folder (guests are offered the folders of their own functions, and the function happening now is preselected); the host decides per folder whether it appears in the gallery and on the wall, and a function-restricted gallery shows each guest only their functions' folders. Team uploads are approved on arrival because they come from people the host chose. The album is made ready lazily on every read rather than by a migration, so it also follows functions added later, and older events with several albums are folded in on first read: the oldest becomes the album, the others become folders, and their QR codes are pointed at the album so printed codes keep working. Folding is idempotent and safe under concurrent reads.

### ADR-038: Site pages are rows; the contact form has an inbox; every checkout ends on a status page (2026-10-07)
About, Contact and the policies were drafts in the web app's source, so changing a sentence needed a deploy, and the payment gateway's review and India's IT and consumer rules need finished policies that name the operator and a grievance officer. Pages are now `site_pages` rows edited in the console by content managers (`page.manage`): a title, a summary, a layout (document with an index, cards, or the contact form) and sections written in a small plain-text markup that `@bulava/validation` parses identically for the site and the console's preview. Company details are placeholders filled from the settings (`{legalName}`, `{address}`, `{grievanceOfficer}`, `{supportEmail}`), and a paragraph whose value is missing is left out, so a policy never shows a half sentence before the details are entered. The finished texts are seeded once as built-in pages (never overwritten by later seeds); built-in pages keep their address and layout and stay published because the footer, checkout and gateway link to them, while new pages can be drafts and be deleted. The site reads published pages with a one-minute cache and treats an unreachable API as an error, not a 404, so a failed refresh keeps the last good policy. The footer lists the pages by column, and its text is a site setting. The contact form saves `contact_messages`, emails the one support address with the sender as reply-to, and is answered from a console inbox (`contact.manage`), whose replies are emailed and kept; a hidden field drops bots, the route is rate limited, trackers never load on the form, and messages are deleted two years after they were last touched (spam after 30 days). Checkout no longer reports its result in a passing message: it always lands on `/dashboard/payments/:orderId`, which shows only what the API recorded (paid, confirming, failed, open, refunded) and polls while a webhook may still settle the payment. Retrying reopens the same Razorpay order, which accepts several attempts and captures at most one, so a retry cannot charge twice.

### ADR-039: Consent is a recorded tick; deleted accounts can be restored for 30 days (2026-10-07)
India's DPDP Act wants consent that is free, specific and given by a clear affirmative action, and the Consumer Protection (E-Commerce) Rules forbid recording a purchase consent from a pre-ticked box. Sign-up (including Google sign-up) and every purchase therefore need an unticked box the person ticks; the API refuses requests without it and records a `consents` row with the policy versions shown (the policy page's last change), so an edited policy is told apart from the one accepted. A new account through Google is created only from the sign-up page with the box ticked; from the sign-in page it is sent to sign up first. Deleting an account used to anonymize it at once, so a mistaken click was permanent. It now takes the owner's events offline and marks the account `PENDING_DELETION` for 30 days: every check that requires an `ACTIVE` account (sign-in, refresh, staff routes) already refuses it, the right password or Google offers a one-use restore token instead of a session, and restoring brings back exactly the events that went offline at the request time. After the window the worker sends a last email and erases the account; its events are purged with their photos, while orders, payments, consents and the audit log keep the bare account id because tax law and accountability require them. Requesting deletion needs the password (or a typed DELETE for Google-only accounts), and staff cannot reactivate such an account, so only the owner decides. The policies gained an account deletion page and a grievance redressal page with the timelines of the IT and e-commerce rules and the escalation routes (Grievance Appellate Committee, National Consumer Helpline, the Data Protection Board).

### ADR-040: Templates can be designed on a canvas; the artboard scales with CSS (2026-10-07)
Section templates compose a page from prebuilt layouts and a theme, so a designer could choose among variants but not place a photo in an arch beside a name, stack a countdown under a date pill or build the card-per-function invitations the market expects; each such idea meant a new React section. A `canvas` section instead stores a design: fixed artboards (phone, optionally desktop) with absolutely placed layers (text, image, shape, ornament, icon, widget), edited in the Studio with drag and drop. The design stays data in the same definition JSON, validated by the same schema and checked by the same matrix, licences and publishing flow, so the rule that templates are data holds. The renderer scales an artboard with CSS alone (percentage positions, `cqw` sizes, a container query choosing the artboard), so a composition keeps its proportions on every screen without measuring in the browser, server rendering and thumbnails stay static, and the phone frame in the Studio stays a phone; only shrinking long names runs in the browser. Colours are palette roles by default, so a canvas design restyles itself with the host's colour preset like every other template, and text is nudged to WCAG AA against the artboard's fill unless a designer opts a decorative layer out (the matrix then reports it). Layers never hold raw storage keys or URLs: image layers reference licensed assets that the definition lists in `assets` and browsers load through the public asset route, and host photos come through bindings. Widgets (countdown, directions, Google Calendar, RSVP scroll, detail rows) are drawn by the engine rather than as free HTML, so a design cannot carry script or arbitrary markup, and buttons open only `https:`, `mailto:`, `tel:` and same-page addresses. Films keep their own scene model; a canvas is a website section.

### ADR-041: Preview before paying: provisional accounts, preview links, the plan checked at publishing (2026-10-07)
The funnel lost most visitors at its first click: "Use this template" led to an email-and-password form, the chosen design was replaced by the free default when the event was created, a premium design could not even be saved without paying, and no page showed a draft to anyone. Hosts in India decide invitations with family on WhatsApp, so the product now gives them something to share first. The template page's quick start creates, in one request, a *provisional* account from a WhatsApp number alone (with the Terms box ticked, and updates on WhatsApp as a separate optional consent), a draft event with the chosen design and the type's functions, and a preview link, then signs the browser in; the link goes to the number on WhatsApp when the integration has a template for it. A provisional account is a real `users` row (`provisional = true`): every tenant route and the dashboard work for it, so the design and the functions are edited in the same place as for any host. What it cannot do is publish, pay, send invitations or add team members (`ACCOUNT_UNVERIFIED`), because those need an account someone can get back into and reach: securing it means a verified code on the number, an email and password, or Google. A number that already has an account is never a way into it: the quick start then requires the code, and codes travel only through the `whatsapp` queue as an approved authentication template. Template tiers are no longer enforced when a design is saved to a draft, only when the event is published; drafts and previews carry the watermark, so a host sees exactly what paying buys. The preview is a per-event unguessable token (`Event.previewToken`, replaceable) rather than a `?preview=1` flag on the public page, because the public page is gated by the access policy and a flag would open private events to anyone who learns the slug; the preview page is read-only, always watermarked and never indexed. The maintenance banner the audit flagged is the announcement setting in the console, not code.

### ADR-042: WhatsApp goes through GetGabs by default; Meta's Cloud API stays an alternative (2026-10-08)
The team runs its WhatsApp Business number through GetGabs, a Meta business partner, instead of its own Meta app: GetGabs does the Meta onboarding, holds the templates and the billing in its panel, and gives an API key. Its send API takes Meta's template message body with the key, the sender number and a campaign added, so a second `WhatsAppProvider` in the worker is all that sending needs; templates, variables, allowances, the queue and failure handling are unchanged, and the provider is a setting (`provider`: `GETGABS`, the default for new settings, or `META_CLOUD`; saved Meta settings and Meta environment variables keep Meta). Two differences shaped the rest. GetGabs' webhook carries incoming chats, not delivery reports, and it is not signed. Delivery is therefore read back per message by the worker at fixed ages (5 minutes, 1 hour, 6 hours, 1 day, 3 days), in windows as wide as the sweep's 10-minute interval, so each message is checked at most five times and nothing is stored to know when it was last checked. The chats webhook is authenticated by a random token in its query string (generated in the console and shown only until saved; Nginx logs no query strings and the API redacts it), and it is used only to mark an invitation read when a guest replies to it. Every report, from either provider, goes through `recordWhatsAppDelivery`, which only moves a delivery forward because reports can arrive out of order; this also fixed Meta's webhook, which let a late "delivered" or "sent" overwrite "read". The console's check opens a GetGabs session with the key and looks up each named template (approved, language, number of variables), and its test message goes through the worker like real ones. Rejected: dropping the Meta provider (it costs nothing to keep, and leaving GetGabs later stays a settings change); polling every sent message on every sweep (hundreds of calls for each unread invitation); accepting the unsigned webhook without a token.

### ADR-043: Google sign-in is configured in the console (2026-10-08)
Google sign-in read its OAuth client from `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, so turning it on or rotating the secret meant editing the server's environment and restarting the API, unlike every other integration since ADR-033. It is now the `google` settings group: an on/off switch and the client ID as values (validated as a Google client ID, which catches a pasted secret), and the client secret as an encrypted, write-only secret, edited by the Super Admin under Integrations with the redirect URI to register shown beside them. `GoogleAuthService` reads the group through the settings store for every flow (cached for 15 seconds), so a change applies without a restart; the environment variables remain the fallback until the group is first saved. The console's check proves the client at Google's token endpoint with a made-up code, which Google answers with `invalid_grant` for a valid client and `invalid_client` for a wrong ID or secret, without anyone signing in. Google's endpoints (issuer, authorization, token, keys) and the redirect URI override stay environment variables, since only tests and unusual deployments change them.

### ADR-044: A guided dashboard: Home, three-step creation, access chosen at publishing, a next step under every page (2026-10-08)
The dashboard read as a set of forms: creation was one long form that asked, before anything existed, who could open the invitation (with invite-only preselected, the mode that needs the most work), the design page squeezed the template grid between two columns until names and previews were cut off, and nothing told a host what to do after creating an event. The dashboard now has a Home (the next celebration's countdown, the event to pick up with its next step, activity and shortcuts) beside My events, and creation is three steps of cards and chips (occasion, who and when, which functions) with a live invitation card. Access moved to the moment it matters: events start as one private link with registration open (the mode a shared WhatsApp invitation needs, as the quick start already did), and the publish dialog asks who can open the invitation, with the private link recommended, sending the mode and the status in one update. The API keeps its `INVITE_ONLY` default for other clients; the dashboard sends `PRIVATE_LINK`, and creation gained `functionSlugs` (the suggestions the host keeps) and `date` (the main function's day, set by the same helper as the quick start). One list of setup steps (`lib/setup-steps.ts`: design, functions, guests, publish, share, replies; guests optional for link-shared events) feeds the overview's checklist, the sidebar's ticks, the home page and a next-step bar under every event page, so they never disagree; the event payload now carries the chosen design, which also gives event cards their cover. Templates are browsed in a full-screen dialog with filters and the gallery's pre-rendered previews, the focused design rendered live with the host's names. The account area is one layout (a route group, so `/dashboard/payments` and its checkout status page keep their addresses) with Profile, Sign-in & security, Payments and Privacy & data. Rejected: a single long wizard that also chose the design (designs need the room of their own page and the browser), and asking for access at creation with a better default (the choice means little before there is anything to share).

### ADR-045: Codes at sign-up and sign-in; Continue with WhatsApp makes accounts too (2026-10-08)
Signing up took an email and a password and signed in at once, without proving the address, and a password signed in by itself. Two things followed: anyone could register someone else's address first (and hold it, receive that person's receipts and invitations, and block them from signing up), and a leaked password was a whole account. The team asked for codes at both points, and for WhatsApp as a full way in. An email account is now made only once the code sent to its address is entered: the sign-up form's details (the password already hashed, the policy versions shown when the box was ticked) wait in Redis with the code for 10 minutes, so an address nobody proved is never saved and never blocks its owner; adding an email to an account made from a WhatsApp number works the same way. A right password is never a session by itself: accounts with an authenticator app keep that as their only second step (the stronger factor, and staff then never depend on email to reach the console), and the others get a code by email that finishes the sign-in and confirms the address of older accounts. The same codes reset a forgotten password, which had no way back before; the reset answers alike for addresses with and without an account. Codes live in `EmailCodeService` under the hash of a challenge token only the starting browser holds: HMAC'd with that token, 5 tries, single use, bound to their step, a new one 30 seconds after the last, with sends and wrong codes limited per address. Because sign-ups now prove their address, Google sign-in links to an existing email account automatically (ADR-027 still holds for older, unconfirmed accounts). "Continue with WhatsApp" sends a code to any number, so the answer never reveals whether a number has an account; a number without one gets a token that makes it with a name and the ticked Terms box. A number saved on an account but never confirmed there signs in only to an account made from it (provisional); any other answers `PHONE_UNCONFIRMED`, since a mistyped number would otherwise hand the account to a stranger, and owners confirm their number from the account page. WhatsApp reports a number that cannot receive messages only after accepting the message, so each code's job has an id the page asks about (`/auth/phone/status`): the worker's result, then GetGabs' read-back or a failure Meta posted to its webhook; `failed` turns the page to Google and email. Without email set up, production refuses email sign-ups and resets (WhatsApp and Google still work) and lets a password sign in alone, so a fresh server's Super Admin can still reach the console to set email up; the console's Email card says so. Rejected: creating unverified accounts and verifying later (an address could still be held by whoever typed it first); asking accounts with an authenticator for an email code as well (a weaker factor on top of a stronger one, and staff sign-in would depend on email); remembering devices to skip the code (not asked for; sessions last 30 days); a WhatsApp sign-in that only works for existing accounts (it either says which numbers have accounts or leaves new people waiting for a code that never comes). ADR-052 later let a password, once set, sign in by itself on the one sign-in form.

### ADR-046: Card illustrations are drawn in code and recoloured by the palette (2026-10-09)
The canvas (ADR-040) placed text, photos, shapes and line ornaments, which made tidy layouts but not the graphics-rich cards hosts expect: elephants, peacocks and temple bells, names in foil, card stock you can almost feel. Commissioned paintings already have a route (ADR-032), but each needs a licence and stays in its painted colours. The card collection therefore uses illustrations drawn in code. There are 28 SVG components in `template-engine/src/art`, built from shared pieces in `art/kit.tsx`: shades and a metal gradient made from one colour, strokes that taper along Bézier curves, and a frame aligned to a curve for placing patterns along a finger or a feather. They need no licence, add no download and render the same on the server, in the browser and in films. They also take the palette: the layer's colour is the illustration's main colour and the palette colours the rest, so a host's preset restyles the art as it restyles the text.

The finishes are schema data like everything else:

- `foil`: a metallic gradient made from the layer's own colour. Text takes it through `background-clip`; line ornaments take it by a scoped override of `currentColor`.
- An ornament `shadow` (soft, or a glow in its colour), a `blend` mode on every layer, and radial gradients with an optional middle colour.
- Artboard `texture`: SVG noise as a data URI, blended so paper reads on light and dark cards.
- The `shimmer` motion, and a `scene` layer that puts an illustrated scene in a frame.

The illustrations follow the scene rules: hash randomness, no raw trigonometry, inline styles and ids from `useId`. This keeps hydration and films stable. Painted artwork remains the route for styles code cannot reach.

Two fixes came with it:

- The inline countdown shows translated short labels. It used to cut each word to three characters, which printed "Hou" and broke Hindi words.
- The seed compares numbers to 15 significant digits. A stored definition comes back with float noise rounded away (0.35 + 0.1 is saved as 0.45), so a catalog template with such a sum was republished on every deploy.

Rejected:

- Shipping the illustrations as image assets: each would need a licence and a recolouring scheme.
- Letting designers paste raw SVG: a design could carry markup, and templates would stop being data.

### ADR-047: The album link is for viewing; entry passes, previews and placeholder functions follow what the host set up (2026-10-09)
Four defaults leaked more than hosts meant.

- **Uploads.** Anyone holding the album link or its QR code (printed on tables, drawn on the live wall) could upload photos into an event's album. Uploading now needs a person: the team (`media.upload`) from the dashboard, or an invited guest from their own invitation when the host turns guest uploads on (`MediaRoom.uploadsEnabled`, now off by default). The guest's token travels in the URL fragment and a header, as for galleries.
- **The gallery and the wall.** The album link, the printed QR code and the wall's QR code open the gallery, which is public by default, with downloads. That is what hosts want a screen at the venue to offer: see and save the photos. Hosts can still narrow it to invited guests, per function, or themselves.
- **Entry passes.** Every invitation showed an entry QR code even when nobody would scan it. Passes are now an event setting, off by default (`Event.entryPasses`); no check-in code is made while it is off. The desk scans passes with the phone's camera in the browser: the native `BarcodeDetector` where it exists, `jsqr` (loaded only when the scanner opens) elsewhere.
- **Previews.** A preview link kept showing the whole invitation after publishing, which would let a link meant for family bypass an invite-only event. The preview now ends at publishing: the API returns only the public page's slug, and the web app redirects there. The dashboard shows the public link only once the event is published.

Placeholder functions also leaked. The event type's suggested functions are created at creation without dates, and they appeared in templates and invitations as empty cards. A function without a date is now a placeholder: templates, invitations and the public page leave it out (`RenderContextService.build`). The functions step is done only once a function has a date, time and venue (`counts.readyFunctions`).

The migration moves existing albums to the new defaults: guest uploads off, invite-only galleries public, downloads on. A host who wants guest uploads turns them on again.

Rejected:

- Keeping "anyone with the link can upload" as an option. Hosts asked for the opposite, and a QR code on a table cannot tell a guest from a passer-by.
- Gating previews by status in the web app only. The API would still serve the full invitation to anyone with an old link.

### ADR-048: The catalog grows by themes from a factory, and lists travel without definitions (2026-10-09)
Hosts asked for hundreds of designs (about 200 for weddings, 100 for birthdays, dozens for every other occasion). Hand-placing every layer of 500 canvas designs would take months and drift in quality; generating them blindly would give 500 lookalikes.

The factory (`templates/src/factory/`) splits the work the way a design studio does. A theme is art direction: a palette and presets, fonts, and which illustration sits where (the kit). A composition is a layout drawn once with fixed zones, so any kit fits it without overlaps. A theme picks the compositions that suit it, and each pairing becomes a template with its own name. 79 themes over 14 compositions make 513 templates. The catalog tests keep it honest: unique names and theme words, no two layouts of a theme with the same composition and art, and the full test matrix for every template. Every theme was reviewed in rendered contact sheets, which is how the rules in docs/templates.md#template-factory came about (round motifs only turn, frames never stand empty, rings only for couples).

The catalog's size changed how it travels. `GET /public/templates` used to cache and return every definition (6.5 MB with the factory); galleries rendered from pre-rendered images and the dashboard picker showed one design live, so almost none of it was used. Lists now carry a small `preview` instead, read with JSON operators in the database, and definitions come per template (`/public/templates/:key`, or `keys=` with `include=definition`, capped at 60), cached in Redis by version id: a published version never changes.

Rejected:

- Generating templates at random from the art and palettes: designs need a designer's choices (which art suits a sangeet, which colours a Christian wedding), and the catalog already had to retire lookalikes (ADR-031).
- Keeping full definitions in the list and compressing the response: Next's data cache refuses entries over 2 MB, and every API request would still parse the whole catalog.

### ADR-049: Digital cards are designed without an account, downloaded free with a watermark, and bought per card (2026-10-09)
Most people who want an invitation want a card for WhatsApp, not a website, and they will not sign up to get one. The card flow had to work for a stranger in a minute, earn money without blocking the free download, and give the team a funnel they can trust.

- **Templates, not a second catalog.** Every canvas template's opening artboard becomes a card (`cardFromTemplate`). Text that shows the event's details stays linked to a Details form; everything else becomes the customer's own words. The three scene-based DIGITAL_CARD templates stay with the event dashboard.
- **One drawing for everything.** The editor, the download preview and the exported image all draw `CardView`; the export is a Chromium screenshot of the web app's own render page in the media worker. Drawing cards a second way (satori, a canvas port) would drift from the editor on container queries, blend modes, foil and fitted text.
- **Anonymous by design.** A card session is a random token kept by the browser (hashed in the database); designs also live in localStorage. Contacts are one row per mobile number. The free download asks for a number only; a purchase also asks for a name and an email, kept with the order for the receipt and disputes. Offers on WhatsApp are a separate, unticked box, recorded as a Consent with the contact.
- **The order is the entitlement.** A paid order freezes the design it buys and settles only on Razorpay's verified signature or webhook, idempotently. Its page is reached by an HMAC token after a `#` (never logged), emailed with the card, and works again for a year: download, email again, make the image again. One open order per design and a design already bought returning its order mean a customer cannot be charged twice.
- **Conversions are facts, not clicks.** Funnel steps that are conversions (a card changed from the template, a downloaded image, a verified payment, a sent email) are written by the server when they happen; the browser may only report steps it alone sees.
- **Plan holders pay nothing.** A signed-in customer whose plan in force removes the watermark downloads clean cards; the Super Admin chooses whether event plans count (`cards.planDownloads`).

Rejected:

- Requiring an account to download: the free card is the funnel's top, and a login wall there loses most people.
- Hiding the watermark with CSS on a client-made image: the free image must be made on the server with the mark in it.
- A per-card OTP for the free download: WhatsApp codes cost money per message, and the number is a lead, not an identity.

### ADR-050: Staff choose the home page's templates; the automatic choice fills the rest (2026-10-09)
The home page picked its templates in code (a hero by key, two phones behind it by key, the first scenes, featured or not), so changing the shop window needed a release. Each section that shows templates now reads staff picks from `showcase_sections` (one row per section: keys in order), chosen in the console's Home page screen by content managers (`showcase.manage`, not a Super Admin setting: it is merchandising, not configuration).

- **Picks first, never an empty section.** The site shows a section's picks in their order and fills what is left with the automatic choice it always made, so a half-filled section still looks complete and a deploy with no picks looks as before.
- **Keys, checked on save and on read.** Picks are template keys (stable across releases and the catalog sync). Saving accepts only published templates that fit the section (a website, a film, or a canvas card) and at most its size; reading skips any that were unpublished since, and the console flags them.
- **The card gallery's Featured order is a section too**, so the cards people see first are chosen the same way.

Rejected: a `featured` flag per template (one flag cannot say which section or in what order) and a JSON platform setting (only the Super Admin edits settings).

### ADR-051: One template per design and occasion; galleries show each design once (2026-10-09)
The factory built each occasion's themes from shared kits, palettes and compositions, so the same design appeared under several names: in one occasion in different colourways (Bandhani Kanku, Gulaab Pankhudi, Gulabi Pankhuri and Mayur Sutra were Sona Sutra recoloured), across occasions with different wording (Rosewood Garden for weddings, Evergreen Garden for anniversaries), and once as a factory copy of a hand-made card (Rajwada Jharokha of Shahi Gajraj). Customers saw the same card again and again.

- **A design is its art, not its colours.** `designLook` hashes the phone artboard's illustrations and their places, on light or dark stock. Palettes, fonts and words are what customers change in every editor, so they do not make a new design; light and dark stock does (a preset cannot turn a light card dark).
- **Same occasion: one template.** The 54 lookalikes are retired (soft-deleted by the seed; cards and events made with them keep working), and the template kept offers their colours as presets. The catalog test now fails on two templates of an occasion with one look.
- **Different occasions: one card in a gallery.** Versions for other occasions stay, because their wording, names and filters differ (an engagement customer still finds engagement cards). Galleries collapse each look to one card: the version for the occasion chosen, else the first in the gallery's order (featured, then catalog order, which puts a design's main occasion first). The look comes with the template list (`preview.look`), so templates staff publish later are grouped the same way.

Rejected: retiring cross-occasion versions too (engagement, anniversary and function customers would lose designs worded for them; wedding designs can switch to engagement wording, but not to an anniversary's or a haldi's), and grouping by pixel similarity (it could not tell a recoloured card from a different couple, which matters to customers choosing by tradition).

### ADR-052: One sign-in form, an optional password that signs in by itself, and a checkout page (2026-10-10)
The product owner's review of onboarding found too many steps between a visitor and their first invitation: separate sign-in and sign-up pages, a password required to sign up, an emailed code after every password, a "Pay" that opened Razorpay at once with a coupon field that gave no answer, and plan limits ("upgrade to add more") with no way to the plans. The goal set was "no hassle of remembering a password anymore".

- **One form.** `/login` has one field for an email or a WhatsApp number, told apart as it is typed (an @ or a letter is an email; digits are a number, Indian when typed without a country code and starting 6–9, shown with India's flag and +91), and Continue with Google. `/signup` redirects there. A number gets a WhatsApp code (unchanged); an email gets a code (`POST /auth/email/start`, step `access`) unless its account has a password, which the form then asks for, with "email me a code" beside it.
- **New accounts are made on one last step**, after the address or number was proved by its code, or by Google: a name, the unticked Terms box and, with an email, an optional password. Google no longer makes an account from the start URL (`consent=1` is gone): a new Google person comes back to the same step through a 15-minute token in the URL fragment (`/auth/google/signup`), so there is one place where the box is ticked.
- **A password, once set, signs in by itself.** This replaces ADR-045's "a password never signs in by itself" at the owner's request: codes are the default way in and a password is the shortcut a person chose. Ten wrong passwords for an address pause the password (not the codes) for 15 minutes, and a code clears the count. Accounts with an authenticator app still finish with it after a password or a code, and staff routes still require two-step sign-in in production, so the console's protection is unchanged (the console keeps `/auth/login`, password then emailed code). A forgotten password is a code away on the form; changing it without the current one uses the reset code from Account.
- **What the form tells.** The start step says whether an address has an account with a password (it must ask for it); addresses without one, new or not, get the same answer and a code. Numbers keep telling nothing. This is the trade-off for one field; the auth routes stay limited to 10 requests a minute per IP.
- **One account, any way in.** An account made with WhatsApp adds an email through its code (no password needed) and an email account confirms its number on WhatsApp; both then sign in to the same account. Google can be disconnected whenever another way in remains (an email, a confirmed number or a password).
- **Checkout before paying.** Plan cards only choose; `/dashboard/checkout` shows the plan, the event it unlocks, the price from `POST /orders/quote` with a coupon applied or refused beside the field, and the terms box, then pays; leaving Razorpay and paying again reopens the same order. Signing in from a plan returns to its checkout (`next`), and someone without an event creates one and comes back. Customer copy says "unlock" instead of "upgrade" (the event's plans page moved to `/unlock`), and plan limits say which limit, with "Click here to unlock".

Rejected: a toggle between email and phone (one more decision for a newcomer); dropping passwords entirely (some people prefer them, and older accounts have them); keeping the email code after a password (the owner's explicit request was a quick return, and the authenticator app remains the second factor for anyone who wants one); answering every address with a code and checking the password afterwards (an account with a password would get an email it did not need on every sign-in).

### ADR-053: Plans belong to the account (2026-10-10)
Standard and Premium were bought for one event: the checkout asked which event, a second event needed a second purchase, and an account's plan showed only inside that event. The product owner's model is simpler: a plan is a one-time fee that gives the account its limits. `POST /orders` now sells one-time plans as well as yearly ones, and the order's grants carry no event, so every event of the buyer's gets them through the account-level path that yearly plans already used (`loadEventFeatures`), with no end date. How many events an account may have at once stays the plan's `events.max` (the Free plan's 1 unless a plan sets its own, in the console), so a one-time plan does not turn into unlimited events. The quote says when the account has the plan, or a higher one, already (`included`, by `templates.maxTier`), and `POST /orders` refuses to sell it again (`PLAN_ALREADY_ACTIVE`). Older orders keep their event, `POST /events/:id/orders` still buys for one event, and the console's complimentary grants still choose an event. A template chosen on an event's plans page travels with the checkout (`event`, `template`) and goes on that event once paid. Rejected: hiding the question and attaching the purchase to the user's only event (the second event would quietly be on the free plan, which contradicts what the buyer paid for).

### ADR-054: Drafts are free; the plan is asked for when publishing (2026-10-10)
Creating a second event on the free plan was refused (`events.max` counted every event that was not archived), so people could not try a second design or prepare an event before deciding to pay. The product owner wants everyone to make as many drafts and previews as they like and to be asked for a plan only when publishing. Creating, copying and quick-starting events no longer check the plan; publishing checks `events.max` against the owner's published events (`ACTIVE` or `COMPLETED`; drafts, archived and cancelled events do not count), next to the design's tier and the secured account it already checked. Guests can open every event that is not a draft (the public page, invitations, the album), so any status change out of `DRAFT` is publishing and runs these checks, not only `ACTIVE`; an archived or cancelled event that becomes active or completed again takes a place again. An event bought on its own (an order for one event) neither counts nor needs a place. The publish dialog shows the limit with "Click here to unlock" (the plans page for the number of events). With plans on the account (ADR-053), Standard and Premium keep the Free plan's count unless the console gives them their own `events.max`; Studio allows 50. Rejected: keeping the check at creation with a higher draft allowance (a number nobody asked for), and counting drafts at publishing (they would block each other).

### ADR-055: Hearts on designs are real likes; the Super Admin decides when counts show (2026-10-10)
The product owner asked for likes on templates and cards, starting from invented numbers (500 shown, 501 after the first real like) with a console switch to publish the real ones, because a gallery full of "0" looks empty at launch. Invented counts were not built: a number saying people liked a design when they did not is false social proof (India's dark-pattern guidelines, CCPA 2023, give "showing false popularity of a product or service" as an example), and the gallery's credibility would rest on it. What was built answers the same worry honestly:

- **Every like is real.** A signed-in person likes a design once (`template_likes`, unique per template and user). A visitor without an account likes once per browser through a random `bulava_vid` cookie set on their first like (httpOnly, one year, sent only to `/api/v1/public`; the database keeps its SHA-256). One network adds at most one visitor like per design a day (Redis), so a script cannot pile them up; a signed-in person is not limited. Signing in turns that browser's like into the person's own, never a second one. `templates.likeCount` changes in the same transaction as the row, and a check keeps it from going below zero.
- **No "0" on show.** Hearts always appear. Numbers stay hidden until the Super Admin switches them on (settings group `likes`: `showCounts`, off by default, on the console's Home page screen) and then show only on designs with at least `minimum` likes (10 by default). Below that, the heart stands alone, which reads as an invitation to like rather than as an unpopular design.
- **Curation stays the social proof.** Staff badges (New, Popular, Bestseller) and featured picks are the signals that exist from day one; the Template Studio list shows each design's likes, so staff can feature what people actually like.

Rejected: invented counts in any form, including a starting number added to the real ones; one like per IP address (households, offices and mobile networks share one); requiring an account to like (most people browsing the gallery have none yet).

### ADR-056: Card JSON becomes a canvas template draft; cards carry up to four functions (2026-10-10)
Card designs arrive as JSON from other tools: a canvas size, a theme (colours and fonts), data, assets and positioned elements (`rect`, `circle`, `line`, `image`, `text`, `button`). The product owner wants that format accepted. `importCardJson` (`@bulava/template-schema`, `import-card.ts`) converts one into a canvas template, and Template Studio has *Import card JSON*: *Check* shows what it became (layers, stand-ins, warnings, validation issues, whether the key is taken) and *Create draft* saves a new draft (`POST /admin/templates/import-card`, `template.manage`, audited as `template.imported`), which staff finish in the Canvas editor and publish like any other template.

- **What converts.** Rectangles, circles and lines (vertical ones as rotated lines), text and buttons with their fonts, sizes, weights, spacing, alignment, opacity and colours. The theme becomes the palette, and an element painted in a palette colour keeps that role, so presets restyle it; a script heading font becomes the script font. The first full-canvas rectangle becomes the artboard's background.
- **Linked, not frozen.** The couple, the date, the venue and the first four functions (`events.N.*` becomes `functions[N].*`, each shown only when that function exists) are bindings, so the design follows the host's details. Other data fields become text slots holding the JSON's words.
- **Images are never fetched.** A licensed asset already in the library (`asset:<id>`) is used, a photo binding becomes a photo spot, and any other picture (a texture, a mandala, a floral border) becomes the nearest drawn art or paper texture and is listed as a stand-in for staff to review. Raw URLs never enter a definition.
- **Checked like a Studio draft.** The conversion must be a valid definition to be saved and its key must be free; semantic issues and missing assets are shown, and publishing refuses them as it does for every template.

Cards needed the timeline these designs carry: a card's details now hold up to four functions (`CardDetails.functions`: name, date, time), edited in the card editor's Details panel, and card text may bind to `functions[0..3].name`, `.date`, `.time`, `.startsAt` and `.venue.name`; layers shown only when a function exists keep that condition on cards, and the API accepts no other condition.

Rejected: downloading the JSON's image URLs into storage (unknown licences, and fetching arbitrary URLs from the server), and a card format separate from canvas templates (two editors and two renderers to keep in step).

### ADR-057: Hosts edit their invitation website on a canvas, like a card; editors come light or dark (2026-10-10)
Hosts could restyle a website template (palettes, fonts, words, photos, motion, sections) but not arrange it: the canvas sections that 470 of the websites are built from could only be changed by staff in the Studio, while card customers moved, resized and restyled everything. The product owner asked for the card editor's freedom on websites, an editor like the design tools hosts know (sections on the left, the phone in the middle with a zoom bar, typography and spacing on the right), and light and dark editors as a personal choice.

- **The host's own artboards.** A customization may hold `canvas`: for each canvas section the host redrew (by section id), their `mobile` and `desktop` artboards. `TemplateRenderer` draws them in place of the template's (`withCanvasCustomization`), so the public page, invitations, previews and thumbnails all show them. They apply only while they fit: the same section at the same size. A newer template version that changes a section falls back to its own design there, and the design page drops arrangements that no longer fit before saving (`fittingCanvasCustomization`).
- **Checked like a template.** `validateCustomization` takes `canvas` only when the template allows layout changes, for sections and artboards it has, at their sizes, and then validates the template with the host's artboards in place: known bindings and words, licensed assets the template lists, at most 120 layers. A button may link only to the event's own details (a binding without a written fallback) or keep the template's address, so an invitation on Bulava's domain cannot send guests to another site.
- **One editor, two homes.** The card editor's stage, inspector and panels now work on any board (`BoardEditorApi`): the card editor gives them a card; the website's canvas editor (`CanvasDesigner`, full screen over the Design page) gives them one section at a time, phone or desktop, and maps their changes back to the customization (the board, the palette, photos into `photoSlots` and `photoIds`). It adds a Sections panel (each canvas section, small, marked when edited), the design page's own Style and Photos panels, a whole-invitation preview and **Restore this section**. Its changes are the page's and save with its **Save**, in one undo history.
- **Premium tools in both editors.** The inspector groups *Typography* (font, the weights the family is loaded in, size, colour, alignment, bold, italic, capitals) and *Position and size* (X, Y, width and height in design units, centring across and up and down). A zoom bar floats over the canvas; on phones the selected element's settings open below it.
- **Light or dark.** `data-editor-theme` on the editor and `editor-chrome` on its bars, panels, sheets and dialogs: dark mode re-maps the site's colour tokens inside the chrome (Tailwind's utilities read them as variables), never on the canvas, so the design keeps its colours. The choice is kept on the device (`bulava.editor.theme`), else the system's.

Rejected: converting websites into cards to edit them (the website's other sections, widgets and per-function cards would be lost); storing the host's changes as patches to the template's layers (a template update would apply them to layers that moved or changed meaning; whole artboards that stop applying when they no longer fit are predictable); a separate dark stylesheet for the editors (every control would need a second look; re-mapping tokens keeps one).

### ADR-058: Canvas invitations become films (2026-10-10)
The catalog's 17 films were each hand-built from text elements over an illustrated scene, so premium films were few while there were hundreds of premium canvas invitations. A film scene may now carry a canvas artboard (`scene.canvas`: the board, a `stagger` between entrances, a camera move and its intensity). The video engine draws the board still and moves each layer itself from the frame number (CSS animations do not follow Remotion's clock, so `CanvasArtboard` takes a `layerStyle` for each layer): layers come in top to bottom, or in the order of their own delays, words rising, photos opening, art fading in, while what covers the board is there from the first frame; the camera drifts as in illustrated films; the website's buttons and live countdown are left out.

`templates/src/canvas-films.ts` films 22 of the strongest canvas invitations (weddings across traditions, the new stationery collection, mehendi, haldi, sangeet, reception, an engagement, a birthday, a baby shower, a housewarming and Diwali): the opening fitted to 9:16 (`fitBoard`), the function card once per function, and the art, photo and names to close. They are ordinary VIDEO templates (validated, checked by the matrix with their canvases, rendered by the video worker), and galleries draw their posters from the opening board until pre-rendered images exist.

Rejected: converting canvas layers into film elements (illustrations, masks, foil and textures have no element equivalent), and CSS animations in films (frames would differ between renders).

### ADR-059: Every website and every film can be designed on the canvas (2026-10-11)
ADR-057 gave the canvas editor to the websites built from canvas sections. The product owner asked for the card editor's freedom on every website template and on video templates as well, keeping the editing hosts already have (tabs on the Design and Video pages) and adding the canvas beside it.

- **One studio.** The editors share `BoardStudio` (`apps/web/src/components/editor/board-studio.tsx`): one board at a time on the card editor's stage, the inspector and panels, a whole-design preview, light or dark chrome, one undo history over the customization, photos placed in the host's photo spots. Each editor says what its boards are, how a change is written back, and which panels and preview it shows.
- **Sections the host adds** (`customization.addedSections`): phone-wide canvas sections (390 wide, 120 to 2400 high, at most 8) placed after any section of the template (`after`; empty: at the end, before the footer), started from *Words*, *Photo*, *Save the date* or *Blank*. Every website template takes them, so templates without canvas sections (the flagship illustrated heroes, the builder's layouts) are designed on the canvas too. `withCanvasCustomization` inserts them; a place that is gone in a newer template version moves the section to the end (`fittingAddedSections`).
- **Films redrawn scene by scene** (`customization.scenes`, by scene id): the film's canvas editor (`FilmDesigner`, from the Video page) shows each scene as a board: a canvas film's own board, or a scene's elements converted to a 9:16 board (`sceneBoard`: words, ornaments, shapes and photo spots, with their entrances mapped to the nearest canvas entrance and a gold sweep as foil) over its illustrated backdrop, which stays with its camera move and particles. `withSceneCustomization` films the host's board in place of the scene's own, still over the backdrop; the scene's duration stays. The film's design is kept on the device (`bulava.film.<event>.<template>`) until the video is made, and the render job carries it.
- **Checked like a template.** Both go through `validateCustomization` when the template allows layout changes (now every film too): their own sections and scenes, the sizes each takes, links only to the event's own details, then the whole template with the host's boards in place (known bindings and words, the template's licensed assets, photos only from photo bindings).

Rejected: converting websites without canvas sections into canvas templates (their illustrated heroes and widgets would be lost); a timeline editor for films (hosts wanted to change what a scene says and shows, not its timing, and a timeline is far harder to use on a phone); keeping film edits only in the page (an hour of design lost to a refresh).

### ADR-060: The template's own sections show on the canvas and can be redrawn on it (2026-10-12)
Opening *Design it on the canvas* on a template without canvas sections showed an empty stage until a section was added, while the preview showed the whole invitation. Hosts read that as a broken editor: they expected to see their invitation and change it.

- **Every part of the page, in order.** The website's canvas editor lists the template's sections, its canvases and the host's own in the order guests see them. A template section is drawn on the stage as the website draws it (a `view` target in `BoardStudio`: shown, not edited as a board), with what can be done beside it: *Redraw on the canvas*, *Hide this section* (never the opening), and *Add your own section after this one*.
- **Redrawn in place.** *Redraw on the canvas* turns the section into an added section that stands in for it (`addedSections[].replaces`; `perFunction` for a timeline drawn once per function). `sectionBoard` (`packages/template-schema/src/section-boards.ts`) builds the board from the section itself: its own values (so the host's details keep filling it), its photo spots, and its look (the hero's illustrated scene as a scene layer, or its ornament, pattern or photo, the theme's colours). The hero, couple, story, quote, countdown, venue, timeline and the text sections (family, travel, stay, gifts, menu) are redrawn; the gallery, RSVP, map, photo sharing, announcements and footer work on their own and stay the template's. `withCanvasCustomization` draws the stand-in where its original was; removing it brings the template's section back. One stand-in per section, never for a canvas or the footer, checked by `validateCustomization`; a stand-in whose section is gone in another template moves to the end and replaces nothing.

Rejected: converting whole templates to canvas templates (their live widgets and illustrated 3D heroes would be lost for everyone); redrawing every section kind (a gallery or an RSVP form is not a picture, and a frozen copy of one would stop working).

### ADR-061: Hosts add scenes to their films and choose the film's size (2026-10-12)
The film canvas (ADR-059) let hosts redraw the film's scenes but not add their own, and every film was 9:16.

- **Scenes of their own** (`customization.addedScenes`, at most 8): a 9:16 board (`FILM_BOARD`) after any scene (`after`; empty: at the end), playing 2 to 10 seconds, started from *Words*, *Photo*, *Save the date* or *Blank*. It plays over the look of the scene before it (`addedSceneOf`: its backdrop, particles and background), so the film stays one piece; a board with its own background covers that. `withFilmCustomization` puts redrawn and added scenes in place; the video engine's metadata uses it, so the length counts them. A film may run 180 seconds at most (`FILM_MAX_SECONDS`).
- **The film's size** (`customization.filmFormat`): tall 9:16 (as designed), square 1:1 or wide 16:9 (`FILM_FORMAT_SIZE`). Scenes stay designed tall: in a square or wide frame the art and particles are sized for the 9:16 stage that fits the frame's height and widen to fill it, and the scene's words, photos and boards stay centred on that stage. The worker renders at the chosen size; the editors and the Video page preview at it.

Rejected: designing every scene once per size (three times the work for every host, and most scenes would never be seen in two sizes); stretching 9:16 layouts to other proportions (names and photos would move apart).

### ADR-062: One-time plans, add-ons and paying the difference (2026-10-12)
The product owner's pricing brief ("Bulava.in — One-Time Pricing Plan") replaced the free tier with paid one-time tiers: no subscriptions, a hidden low price for people about to leave, add-ons with their own prices (a video later, without buying a bigger plan), and unlocking a bigger plan for the difference.

- **Plans and add-ons are rows** (`pricing_plans.kind` PLAN | ADDON, `visibility` PUBLIC | HIDDEN, `badge`, `tagline`, `stackable`, `offeredTo`), edited in the console (Pricing). The seed starts with Lite ₹159 (hidden), Starter ₹299, Standard ₹599, Premium ₹999 (Most popular, the first with the MP4 video), Ultimate ₹1,999 and Grand ₹2,999 (done-for-you, priority support), and the add-ons MP4 video (+₹300, up to Standard), remove the mark (+₹149, Lite), one more function, one more celebration, 1,000 more photos (+₹199, +₹199, +₹149, as many as wanted), done-for-you (+₹499) and same-day delivery (+₹199). Studio (the yearly planner plan) is hidden from the consumer pages. Prices include GST.
- **The free plan designs, it does not publish.** `events.max` is 0 on FREE: drafts, previews (watermarked) and every editor stay free, and publishing asks for a plan (`PLAN_LIMIT_REACHED`). What guests see is held to the plan when publishing: the template's tier, the functions with a date (placeholders do not count) and the guests.
- **Add-ons add.** Entitlements from add-ons (`sourceType` ADDON, the limit times the quantity) add to the plan's limits (`withAddOns`; an unlimited limit stays unlimited, a switched-off one starts from nothing) and switch features on as generously as the plan allows. An add-on needs a plan it is offered to (`ADDON_NEEDS_PLAN`, `ADDON_NOT_OFFERED`) and is bought once unless stackable (`ADDON_ALREADY_OWNED`).
- **Paying the difference.** A bigger one-time plan is quoted and charged at its price less the account's biggest one-time plan (`orders.creditMinor`); a smaller or equal one is included (`PLAN_ALREADY_ACTIVE`). A checkout reopened later is refused when the credit no longer matches.
- **The hidden plan is offered, never listed.** `POST /orders/offers` signs a 24-hour offer for the signed-in account (HMAC, `planOfferToken`), only for a first plan (`OFFER_NOT_AVAILABLE`); the checkout makes it on exit intent. Another account's offer is not found.
- **Only the owner buys** (`billing.manage`, the owner's alone): the rest of the team sees what the plan includes and who can unlock more. Customer copy says "unlock" and names one-time payment and GST.
- **What plans now switch:** online replies (`rsvp.enabled`, `RSVP_NOT_TAKEN`), music (`music.enabled`) and the owner's own link (`link.custom`: `/e/<their-name>`, the old link answering `EVENT_MOVED` with the new one, `event_slug_aliases`, never given to another event: `SLUG_TAKEN`). The FREE baseline keeps replies and music on, so invitations published before keep working. Free card downloads are a console setting (`cards.freeDownloads`, off by default); plans include downloads.

Rejected: subscriptions (the brief, and families buy once for one celebration); a coupon for the low price (it would leak; a signed offer is bound to one account and expires); per-event plans for new purchases (kept for API clients and older orders; the account's plan covers its events).

### ADR-063: A design page for everyone, and a blank canvas (2026-10-12)
The product owner asked for canvas editing for every visitor, signed in or not: choose a website, a video or a card, see the designs for the occasion (or start from an empty canvas with every tool), edit and preview freely, and need a plan only to publish or download.

- **/design** asks what to make, for which occasion, and offers the blank canvas first, then the designs (one per look). Cards open the card editor (already open to everyone, with card sessions). Websites and films open the canvas editors (`CanvasDesigner`, `FilmDesigner`) on sample names and photos (`sampleRenderContext`), at `/design/website/<key>` and `/design/video/<key>`.
- **Kept on the device.** A design made there is a local draft (`bulava.design.<kind>.<key>`, `lib/design-drafts.ts`), nothing on the server, so no account is needed and nothing is stored for strangers. The previews are watermarked. Photos come with an event: before signing in, the editors say so (the template's sample photos show where they go).
- **Publishing goes through the account.** *Publish…* and *Make my video…* open the new-event flow (`/dashboard/events/new?template=…&type=…&studio=website|video`), which asks to sign in first (`/login?next=` keeps the whole address); the event is created with the design (a website's customization, checked by `validateCustomization`, or the film's draft moved to `bulava.film.<event>.<key>` for the Video page), and publishing or making the video asks for the plan as everywhere else.
- **The blank canvas is a catalog template** (`blank-canvas`, every occasion, free; `templates/src/blank.ts`): plain paper with the names and date, a function card, RSVP and footer. Its opening is also a blank card, and its film (`blank-canvas-film`) a blank film. Galleries, the sitemap and the home page leave it out (the `blank` tag); the design page and the editors' pickers offer it.

Rejected: anonymous events on the server (accounts and data for every passer-by, and drafts to clean up); a separate blank editor (the existing editors, with their checks and their output, already do everything a blank canvas needs).

### ADR-064: Stock photos and illustrations from licensed libraries (2026-10-12)
Hosts asked to search for images (photos, elements) from outside, "like Google or stock images". A web image search returns images nobody licensed to us or to the host, so the editors search licensed libraries instead.

- **Pexels** (photos) and **Pixabay** (photos and illustrations), with the platform's API keys (Integrations: the `stock` settings group, keys in `SETTING_SECRETS`, a *Check* that runs a real search). Off until the Super Admin switches it on; `GET /public/stock/status` says what the editors may offer, never a key.
- **Searched by the server** for someone editing the event (`GET /events/:id/stock`, `event.update`) or a card being made (`GET /public/cards/session/stock`, by card session), cached (Pixabay asks for a day) and kept within each library's rate limit (a Redis budget per window), so a busy evening never gets a key blocked. Results carry the library's small preview and the photographer, and the panel names and links the libraries.
- **Brought in by the server.** Choosing an image sends only its library and id (`pexels:123`); the server asks the library's API for the file, downloads it from the library's own servers only (redirects included), at most 15 MB, and checks the bytes are the image type claimed. It is then stored like an upload: an event's design photo (`media.stock_imported`, counted against the plan's photos, credit kept as the uploader name) or a card's photo, and the media worker re-encodes it.

Rejected: Google Images or any web search (no licence); hotlinking the libraries' images in designs (private storage, signed URLs and the export renderer need our own copy, and Pixabay forbids it); letting the browser send a file address (the server would fetch whatever it was told).

### ADR-065: The website canvas as one page, and click-to-edit any template section (2026-10-12)
The website's canvas editor showed the page as separate boards, one per section, unlike the invitation guests see; its template sections could not be edited where they stood, its phone was a thick old frame, and the dark editor had a white line along its top.

- **One page, one flow.** The editor draws the whole website with the template's own renderer (`TemplateRenderer` `wrapSection`) inside a frame of the phone's width (390) or a desktop's (1440): `FrameDocument`, an iframe that copies the app's styles and portals the page into itself, so the page lays out exactly as on guests' screens. Canvases and the host's sections are live stages at scale 1; the frame is zoomed as a whole. Every part has its tools on the page (move up and down, hide, restore, delete) and a "+" between parts for a new section there.
- **The host's order** (`customization.sectionOrder`, at most 80 keys): the template's sections and the host's own, a redrawn section keyed by the section it stands in for; the opening stays first and the footer last (`withSectionOrder`), keys must be known and unique (`validateCustomization`).
- **The page's width, not the window's.** Template sections answer to container queries (`@min-[640px]:`) inside a container around the sections (never the root: the intro, music and effects are fixed there), so a phone-wide frame or preview shows the phone's layout on a desktop browser. Screen-high heroes read `--bulava-screen` (the editor's phone screen, 844 px), so a frame's height never feeds back into the page's.
- **Click any template section to edit it like a card.** The click makes the section the host's in its place (a stand-in, ADR-060) without redrawing it from a description: the board keeps the template's own section behind (a `section` layer, by section id: the template's own drawing, words hidden while the host's text layers carry them, laid out on the phone's width and screen and zoomed with its board, inert and hidden from screen readers) and every run of words in it becomes a text layer where it stands, measured from the page: font role, size, weight, letter and line spacing, case, alignment, colour (a palette name when the engine reaches the same ink from it, so colour changes still apply), glow and opacity. Words from the event's details stay bound (`{{couple.partnerOne}}`, dates in their format, the template's own headings as translation keys); a directions link becomes a directions button. The clicked words are chosen. Photos, ornaments and a ticking countdown stay in the drawing; the host can hide the drawing for a plain background. On the desktop page the editor turns to the phone first. A timeline (one card per function) is still laid out afresh (`sectionBoard`).
- **Where a section layer may be.** Only in a redrawn section, for the section it stands in for, once (`validateCustomization`); never in a template's definition, a canvas override, a film or a card. The section is drawn from the template itself, so a saved design carries none of its content and the link rules hold.
- **The editor's chrome.** A bezel-less phone (`PhoneFrame`: a 5 px rim, an island camera) for the editors and previews; dark mode overrides the clay shadows on the elements themselves, so no light rim shows.

Rejected: redrawing clicked sections from a description of each template variant (it lost glows, lines and type, and would drift with every template); scaling the drawing with a script (canvas rendering stays CSS-only: container-query zoom steps, exact where CSS divides lengths); an auto-height page frame (screen-high heroes grew with it).

### ADR-066: The plan an event runs on, add-ons for it, and limits held at publishing (2026-10-12)
A host with a complimentary Starter plan for one event saw "No plan yet" on the plan page (it read only the account's plans) while the event's header said "Standard plan" (it guessed the name from the designs the plan allows), and could not add add-ons at all.

- **The event's plan, by name.** `GET /events/:id/plan` answers the plan an event runs on: the bigger of the owner's account plan and a plan bought or given for that event alone (`scope` ACCOUNT | EVENT, `complimentary` for the team's grants), the owner's account plan (what a bigger plan is paid against), the add-ons that add to it (the account's and the event's own), what it has with them, and what it uses of each limit (functions with a date, guests, photos, videos, WhatsApp messages). The event's header, its plan page and the meters read it; `GET /orders/plan` lists plans of single events (`eventPlans`) after the account's own.
- **Add-ons for an event's own plan.** Bought from an event (`eventId` in `POST /orders/quote` and `POST /orders`, the owner's event only), an add-on adds to that event's plan when the event's own plan is bigger than the account's (the order and its entitlements are the event's); otherwise it is the account's as before. Without any plan the plan pages still show the add-ons, waiting for one.
- **The console's grants are the account's,** as purchases are (ADR-062): a one-time plan given without an event covers every event; an event may still be chosen. Revoking a grant ends an add-on's entitlements as well as a plan's.
- **Limits held at publishing, never in a draft** (ADR-054): a draft takes any number of functions and guests, a new event gets every suggested function (placeholders until dated), and publishing asks for a plan it fits; a published event takes another dated function or another guest only within its plan. Photos, videos and WhatsApp messages are counted when they are made or sent.
- **Saying what a plan leaves out.** A plan without replies or music says so on the replies page and beside the music; a feature the plan does not have names itself (`PLAN_UPGRADE_REQUIRED` with its feature), and every unlock link leads to the event's plan page (or the account's).

Rejected: moving existing per-event grants to the account (they were given for one event on purpose); naming plans from their features (names are rows the console edits).

### ADR-068: Design, one function, publish: guests later, replies by choice (2026-10-12)
Hosts dropped off between creating an event and publishing it: the setup asked for guests and groups before publishing, a wedding started with six placeholder functions, and replies were always on.

- **The order** (`lib/setup-steps.ts`): the design, a function (its date, time and venue), publishing; then guests (optional), sharing and, while the host takes replies, replies. A new event takes two steps (the occasion; then the names, the date and the language) and starts with the occasion's main function; groups and guests wait until the host wants them.

Off (or on a plan without replies), the invitation leaves out its RSVP section, canvas RSVP buttons and the registration form, guests' replies are refused (`RSVP_NOT_TAKEN`), and the dashboard hides the RSVP page and its setup step.
- **The parents' names.** The couple's details take each partner's father and mother (`partnerOneFather`, `partnerOneMother`, `partnerTwoFather`, `partnerTwoMother`), asked when the event is made (optional) and in Settings with the couple's names. The render context carries them (`couple.partnerOneFather`…, and `couple.partnerOneParents` / `partnerTwoParents` as "Father & Mother"), and they fill the templates' family lines (`custom.partnerOneParents` / `partnerTwoParents`) unless the host wrote their own there.

Rejected: asking for guests before publishing (a published link works for everyone it is shared with; personal invitations can follow); a reply limit by count (the plan's guests already bound it).
