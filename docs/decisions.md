# Architecture decisions

Short records of decisions that are costly to reverse.

### ADR-001: Stable major versions (2026-09-27)
We use TypeScript 5.9, NestJS 11, Prisma 6, Next.js 15, Zod 4, Tailwind 4, Jest 29 and Vitest 3. Newer majors exist (TypeScript 7, NestJS 12, Prisma 7/8, Next 16), but the previous majors have mature, proven interoperability. Upgrades are planned deliberately, one at a time.

### ADR-002: UUIDv7 primary keys
UUIDv7 ids are time-ordered, which is good for B-tree locality and cursor pagination, and non-sequential, so they are safe in URLs. There are no separate public ids.

### ADR-003: Separate models for event, function, audience and access policy
`AccessPolicy` is its own table, owned by an event (required) or a function (optional override). Audience is `FunctionAudienceGroup` plus `FunctionGuest`. Invitation scope is `Invitation.functionId`. This follows the spec's rule that the four concepts must never collapse into one permission field.

### ADR-004: One pure access evaluator
All guest-visibility decisions go through `evaluateFunctionAccess` in `packages/auth`. It has no I/O and is exhaustively unit tested. The host dashboard's access matrix uses the same function.

### ADR-005: GROUP_RESTRICTED is strict
Under `GROUP_RESTRICTED`, a direct `FunctionGuest` assignment is not sufficient; the guest must be in an audience group. Otherwise the mode would be indistinguishable from `INVITE_ONLY`. An explicit deny still applies.

### ADR-006: Invitation tokens are hashed and encrypted
Lookup uses SHA-256 of a 256-bit token. Hosts need to copy links repeatedly (WhatsApp sharing), so an AES-256-GCM ciphertext is also stored under `TOKEN_ENCRYPTION_KEY`. A database leak alone reveals no usable links. Rotating the key requires regenerating links.

### ADR-007: Tenant routes are nested under /events/:eventId
The spec lists flat routes (`/api/v1/guests`). We nest them (`/api/v1/events/:eventId/guests`) so the tenant id always comes from the path and one guard enforces membership before any handler runs.

### ADR-008: Web proxies the API on the same origin
`/api/v1/*` on the web origin is rewritten to the API. Auth cookies are first-party and httpOnly, CSRF protection is simple, and guests never need cross-origin requests. The API keeps CORS for the admin app and other clients.

### ADR-009: Custom header CSRF instead of double-submit tokens
All mutations need `X-Bulava-CSRF: 1`, together with SameSite=Lax cookies and an Origin allowlist. It is simpler than synchronizer tokens and equally strong while the API's CORS allowlist stays strict.

### ADR-010: Invitation opens and link previews
Each API view increments the token's use count, which is what enforces single-use links. The web page therefore answers known link-preview bots (WhatsApp, Facebook, Telegram and others) with a generic page and never calls the API for them.

### ADR-011: Event categories, languages and plans are data
They are stored in `event_types`, `languages` and `pricing_plans` / `plan_features`, and seeded idempotently. Admins change them without a deploy, and category-specific details are validated by `Event.details` schemas keyed by `detailsSchemaKey`.

### ADR-012: Non-destructive e2e tests
Prisma blocks `migrate reset` when run by AI agents, and resetting shared databases is risky anyway. The e2e suite uses `migrate deploy` and unique data per run instead of wiping.

### ADR-013: SeaweedFS for local object storage
The MinIO image was unavailable from both registries during development, so the local S3 stand-in is SeaweedFS. Code only speaks the S3 API through `@bulava/storage`, so production uses Cloudflare R2 unchanged.

### ADR-014: A separate admin app on its own domain
The staff console is `apps/admin` on `admin.bulava.in`, proxying `/api/v1` like the web app. Staff and customer sessions never share cookies, the console can be put behind an IP allowlist or Cloudflare Access independently, and customer bundles carry no admin code. `/users/me` exposes platform permissions as a UI hint; enforcement stays in `PlatformPermissionGuard`.

### ADR-015: Openings, motifs and music live in the engine, not in templates
Signature openings (lanterns, gates, seal, petals, celestial, scratch), hero variants and ornaments are engine features that templates select by name. Templates stay pure data, every template can use every feature, and all of them are covered by the same tests. Music starts only on the opening's user gesture, because browsers block autoplay.

### ADR-016: Prebuilt Remotion bundle in the video image
Bundling the Remotion project needs webpack and the TypeScript sources of workspace packages. The image bundles once at build time and the worker serves that folder, so production containers start instantly and carry no sources.

### ADR-017: Registrations create real guests with invitations
A confirmed registrant becomes an ordinary guest with an event-wide invitation, instead of a parallel "attendee" model. RSVP, galleries, announcements and check-in work unchanged, and access is still decided by `evaluateFunctionAccess`. Capacity is enforced under a row lock on the event's registration settings.

### ADR-018: Scheduled lifecycle and retention in the general worker
Completing, archiving and purging events are repeatable BullMQ jobs, not cron on the host, so they run once across replicas. Purges delete storage first and keep orders, entitlements and audit rows (plain `eventId` columns).

### ADR-019: Lint once at the root
`eslint.config.mjs` lints the whole monorepo with the TypeScript, React Hooks and Next.js plugins. Next's per-app lint during `next build` is disabled to avoid a second, differently configured pass. `consistent-type-imports` is deliberately off: NestJS dependency injection needs constructor parameter types as runtime values.


### ADR-020: Two-step sign-in with TOTP, required for staff
Authenticator-app codes (RFC 6238) and one-time recovery codes, implemented in `packages/auth` without new dependencies. Password sign-in for such accounts yields only a short-lived challenge, never a session; the session row and access token record that the second factor passed, and `PlatformPermissionGuard` requires it for staff when `STAFF_MFA_REQUIRED` is on (always in production). Codes are replay-proof through a stored last step claimed with a conditional update. Lost devices are reset by an operator CLI, not by support staff in the UI.

### ADR-021: Seating and logistics are not access
Tables live in `SeatAssignment`, not in `FunctionGuest`, because a `FunctionGuest` row is a direct assignment that grants entry. Seating a guest can never change who may attend, and guests only see seats for functions `evaluateFunctionAccess` shows them. Stays and travel are per guest, shown only to that guest, and deleted with the guest.

### ADR-022: Live photo walls use secret, rotatable links
A venue screen has no account and no invitation, so each album's wall has its own 256-bit link (hash for lookup, ciphertext for re-display), opt-in, rotatable and closed with the event. The wall exposes only approved, shareable images through short-lived signed URLs, and the client keeps each image's first URL so polling does not re-download photos.

### ADR-023: Reminders are dispatched only by the worker
The API stores reminder schedules; a per-minute repeatable job claims each due reminder with a conditional update and creates its notification rows in the same transaction, then re-queues any rows left `QUEUED`. Audience fact loading moved to `@bulava/database` so the worker and the API evaluate access identically. Delivery re-checks the situation (replied, moved, cancelled) and skips instead of sending stale reminders.

### ADR-024: Update schemas are built without defaults
Zod 4 applies `.default()` values even inside `.partial()`, so a partial PATCH built from a create schema silently reset omitted fields (album moderation and download settings, RSVP question options and scope). Update schemas are now derived from default-free field sets, with a regression test.

### ADR-025: Server-side template filtering, lighter previews and blocking metadata
Gallery previews are live markup, and the App Router ships every server-rendered element twice (HTML and the RSC payload). Passing all cards to a client-side filter made the gallery 1–1.5 MB and the homepage 1.8 MB. Filters are now links resolved on the server, the gallery pages at 24 cards, previews render two sections, and the template animation styles are one hoisted `<style>` per page instead of one per thumbnail: the homepage is 0.9 MB (91 KB gzipped) and the gallery 0.4 MB (85 KB). Separately, streamed metadata raced with hydration under CPU load (React #418 on dynamic pages, reproduced with a CPU-saturation replay); metadata is rendered in `<head>` (`htmlLimitedBots: /.*/`).

### ADR-026: Templates choose colours; the engine guarantees readable text
Template palettes are designer data, and many pair light accents with light backgrounds. `themeStyle` keeps the palette for decoration and publishes contrast-corrected "ink" variables for text (`--t-primary-ink`, `--t-accent-ink`, `--t-muted-ink`, `--t-on-primary` and so on), computed with `ensureContrast` so each reaches WCAG AA (4.5:1) on every background it can sit on. Engine sections use the ink variables for text, so every current and future template passes without hand-tuning, and the check runs in axe over all previews and openings. Opening labels breathe with a scale animation instead of fading, because opacity animation drops contrast mid-cycle.

### ADR-027: Google sign-in never merges into unverified accounts
Google sign-in (OIDC code flow with PKCE, verified with `jose`) keys accounts by the Google subject. Bulava does not verify email addresses at sign-up, so an existing account with the same email is linked automatically only if its email is verified; otherwise the owner links Google while signed in. Auto-merging would let anyone who registered someone else's address first take over that person's Google sign-in. The flow's state is single use in Redis and bound to the starting browser by an httpOnly cookie, and two-step sign-in still applies after Google.

### ADR-028: Nonce CSP for private pages, static CSP for marketing
A nonce requires rendering per request, and the marketing pages are pre-rendered and cached. Middleware therefore applies a nonce policy with `'strict-dynamic'` to every route that handles accounts, guests or event data (`lib/private-routes.ts`, rendered with `force-dynamic`), and to the whole admin console. Pre-rendered marketing pages keep the static policy with `'unsafe-inline'`. Policies are built once in `next.config.ts` and handed to the middleware through build-time `env`, so there is a single source. Third-party analytics load from a client effect, never inline, and never on private pages.

### ADR-029: Custom domains are aliases, proven by DNS, with certificates from Cloudflare for SaaS
A customer domain is an alias for one event: the web middleware maps its host to the event slug through a cached API lookup, serves the event page at `/` plus guest links, and redirects everything else to the main site. There are no per-domain Nginx blocks; the default server accepts any host, and certificates come from Cloudflare for SaaS (custom hostnames) behind a single fallback origin. Ownership is proven with a TXT record. Claims are not unique until verified (a partial unique index), so nobody can squat a name, and a lapsed verified claim gives way to a newer proof. `EventLinksService` is the one place that decides a guest link's origin, and it also feeds the CSRF allowlist. Active domains are re-checked daily and switched off after three failures, so a domain that changes hands cannot keep serving an event.

### ADR-030: Bulava shares a server behind its existing Nginx
The first target server already runs several sites: its Nginx owns ports 80 and 443, certbot manages every certificate, and other Compose projects publish their own ports. Bulava therefore no longer terminates TLS or publishes 80/443. `bulava-nginx` became an internal router, published only on `127.0.0.1:${BULAVA_HTTP_PORT}`, with host names rendered from `.env.production` by the image's envsubst. The server's Nginx gets one generated site file: a single server block, no http-level names and no `default_server`, so it cannot collide with other sites. Certbot handles TLS the same way as for the rest of the server. Real client IPs cross the loopback hop in `X-Real-IP`, which is trusted only from loopback and Docker ranges. CPU and memory limits became settings, because a CPU limit above the host's count stops a container from starting. Video rendering became an opt-in Compose profile, because it can saturate a small shared machine. The same layout works on a dedicated server; Cloudflare stays optional.

### ADR-031: Illustrated scenes are shared data; looks restyle sections; lookalikes are soft-deleted
Premium invitations in this market are illustrated and layered (temples, palaces, torans), and customers compare them with hand-painted video invites. We draw the art in code instead of shipping bitmaps: no image licences to track, every colour change recolours the art, and pages stay light. Each scene is data (`sceneArt`: a background and layers with a depth), laid out on one 1200×800 canvas with inline styles, so the same artwork is a parallax website hero, a Remotion film backdrop with a camera move, and a catalogue poster. Film text is fitted by measuring the real font in the renderer's browser rather than estimating, because estimates clipped long capitalised titles. Section appearance comes from a template-level `look` (bands, frames, card styles) rather than new section code, so one set of sections serves heritage, noir, royal, garden and celebration designs. Hosts get more freedom through capabilities, not new templates: named photo spots, font pairings, free colours on top of presets, openings, effects and hidden sections, all validated against the template and against the event's approved photos. Templates that looked alike were retired with a `deletedAt` soft delete (catalog list or admin action) instead of deletion, so events that picked one keep their pinned version.

### ADR-032: Commissioned paintings are layered assets on the scene canvas
Code-drawn scenes cannot match hand-painted art, so templates can also use commissioned paintings. Rather than a second rendering path, a painting is delivered as full-canvas transparent layers on the same 3:2 canvas as the drawn scenes and becomes the same `SceneArt` (one SVG `<image>` per layer), so parallax heroes, film camera moves, phone framing and posters needed no new code. The layers are licensed assets listed in the definition's `assets`, which keeps the existing licence gate at publishing. Storage stays private: a public route redirects to a short-lived signed URL only for approved, currently licensed images used by a published template version, signed at the top of the hour so browsers can cache it. Versions keep serving after a template is unpublished or deleted, because events stay pinned to them. The media worker makes 1200 and 2400 px WebP renditions (a phone shows only the middle third of the canvas, so heroes need the larger one) and never alters the licensed original. Films wait for every layer to decode before capturing a frame. Artwork lives in each definition, not a shared library, so published versions stay immutable; it moves between templates by duplicating a template or through the Studio's JSON tab. Painted art does not follow palette changes; a second colourway is a second layer set.

### ADR-033: The Super Admin runs the site from the console; one Super Admin, staff roles by area (2026-09-29)
The owner needed to change branding, SEO, trackers and integrations without a deploy, and to give staff narrower access than "platform admin". Site settings and integrations moved from environment variables into `platform_settings`, one row per group (site, SEO, tracking, code, payments, email, WhatsApp, maps, domains), edited only with `settings.manage`. Each group has a Zod schema and is saved whole; its keys and passwords sit beside the values, AES-256-GCM encrypted under `TOKEN_ENCRYPTION_KEY`, write-only (the console sees "set" and the last four characters) and never logged. A group that was never saved falls back to the old environment variables, so running deployments keep working, and its first save copies them over. The API and workers read settings through `SettingsStore` with a 15-second cache, so changes apply without restarts; workers rebuild a provider only when its settings change. Storage stays in the environment: every service must agree on the bucket, and moving it from a form would orphan existing files, so the console only shows and tests it. Public pages read a secret-free `GET /public/site-config`; trackers and header/footer code load from a client effect on marketing pages only, never on private pages (which keep their nonce CSP), and the marketing CSP gains exactly the hosts they need, as plain `https://host` sources. Staff access became six roles by area (support, content, finance, platform admin, Super Admin, plus customers), still enforced per permission. There is exactly one Super Admin: a partial unique index enforces it whatever the code does; the role is handed over with the owner's password and two-step code instead of being assigned; the seed only fills an empty seat, so deploys never take it back; and the CLI can move it for recovery. Complimentary upgrades are zero-amount `ADMIN_GRANT` orders that grant entitlements through the purchase code path, so payment history, access checks and revocation need nothing new; they cannot be refunded and are left out of revenue. WhatsApp Business sends approved templates through Meta's Cloud API from the worker. Each plan has a per-event message allowance, and host sends and scheduled reminders count it under one transaction-scoped advisory lock per event, so concurrent sends cannot overspend it; permanent Meta errors are recorded as failed and are not charged.

### ADR-034: Marketing motion is CSS above the fold and GSAP below it; no WebGL (2026-09-30)
The first homepage hero drew a three.js particle field and an aurora canvas behind the phones. They showed as a hard-edged panel on the dark background, cost a WebGL context and the three.js bundle, and animated only after hydration, so the phones appeared, vanished and animated in again. The redesign ([web-design.md](web-design.md)) lights dark sections with CSS radial gradients and film grain instead, and removes three.js and react-three. Anything visible on arrival (hero words, phones, status chips) animates with CSS keyframes that play from the first paint; sections further down reveal once with GSAP ScrollTrigger, which never runs before the visitor scrolls there. 3D is CSS perspective (the hero rig, template cards that lean toward the pointer), which composes with live HTML invitations. Lenis smooth scrolling stays on marketing pages only, never in the dashboard or on guest pages, where panels and forms scroll on their own. Every effect is off for reduced motion. Sections declare `data-header-tone` so the adaptive header needs no per-page code.

### ADR-035: Link modes share one link and take registrations by default; secret links expire (2026-10-01)
Hosts of public and private events expected to publish and then share a link on WhatsApp, but the only links Bulava produced were personal invitations, so they had to add guests one by one even when they wanted anyone with the link to come. The access modes now split into link modes (`PUBLIC`, `PRIVATE_LINK`, `SECRET_TOKEN`), shared with one link shown on the overview and the Invitations page, and personal modes (`INVITE_ONLY`, `GROUP_RESTRICTED`), which still need guests and invitations. Link modes take registrations by default, so the link alone fills the guest list; the default is applied when an event becomes link-shared and when a link-shared event has never saved a setting, never over a host's later "off". `SECRET_TOKEN` used to mean "invite only" in practice; it is now what its name says: the page opens only with a secret key in the link. The key is 256 random bits, stored as a SHA-256 hash and AES-GCM ciphertext so the host can copy it again, and it expires (a week after the event by default, at most a year ahead) and can be replaced, which a printed or forwarded link otherwise never could be. Keys in URLs leak through history and `Referer`, so the web middleware moves the key into an httpOnly per-event cookie and redirects to the clean address; the API accepts it from that cookie or a header. Guest visibility is still decided only by `evaluateFunctionAccess`, which learned the verified-link viewer.

### ADR-036: Team members are invited by email with a one-use code (2026-10-01)
Adding a team member required them to have a Bulava account first, which made hosts ask photographers to sign up before they could be added. Now an email without an account gets an invitation: a link and a 6-digit code. The person opens the link, enters the code, then chooses a name and password, and joins signed in, with the email marked verified because receiving the code proved it. The code has no time limit, as requested, because photographers are often booked weeks ahead; instead it works once, and five wrong codes lock the invitation until the host sends a new one, which bounds guessing at five tries per invitation against a million codes. Link and code are separate secrets (a 256-bit token for the link, the code for the person), both stored only as hashes. The code is an HMAC under a server key and bound to the invitation, like guest OTP codes, because a plain hash of six digits would fall to a million guesses from a copy of the database. The email job is removed from the queue once sent. If the email gains an account in the meantime, the person signs in and joins with the code, and only as that email. The dashboard now follows the role: the API returns the member's permissions with the event, the web hides sections and actions the role cannot use, sends photographers straight to Photos, and explains a section outside the role instead of showing a generic error. The API still enforces every permission.

### ADR-037: One album per event, with a folder per function (2026-10-01)
Hosts created several albums with different links and QR codes, and guests and photographers did not know which to use. Every event now has exactly one album (a partial unique index on `media_rooms.is_main`): one upload link and QR code, one gallery, one live wall. Photos are organised in sub-albums (`MediaAlbum`): one per function, created and renamed with the function, a General one, and any the host adds. Uploaders pick a folder (guests are offered the folders of their own functions, and the function happening now is preselected); the host decides per folder whether it appears in the gallery and on the wall, and a function-restricted gallery shows each guest only their functions' folders. Team uploads are approved on arrival because they come from people the host chose. The album is made ready lazily on every read rather than by a migration, so it also follows functions added later, and older events with several albums are folded in on first read: the oldest becomes the album, the others become folders, and their QR codes are pointed at the album so printed codes keep working. Folding is idempotent and safe under concurrent reads.

### ADR-038: Site pages are rows; the contact form has an inbox; every checkout ends on a status page (2026-10-07)
About, Contact and the policies were drafts in the web app's source, so changing a sentence needed a deploy, and the payment gateway's review and India's IT and consumer rules need finished policies that name the operator and a grievance officer. Pages are now `site_pages` rows edited in the console by content managers (`page.manage`): a title, a summary, a layout (document with an index, cards, or the contact form) and sections written in a small plain-text markup that `@bulava/validation` parses identically for the site and the console's preview. Company details are placeholders filled from the settings (`{legalName}`, `{address}`, `{grievanceOfficer}`, `{supportEmail}`), and a paragraph whose value is missing is left out, so a policy never shows a half sentence before the details are entered. The finished texts are seeded once as built-in pages (never overwritten by later seeds); built-in pages keep their address and layout and stay published because the footer, checkout and gateway link to them, while new pages can be drafts and be deleted. The site reads published pages with a one-minute cache and treats an unreachable API as an error, not a 404, so a failed refresh keeps the last good policy. The footer lists the pages by column, and its text is a site setting. The contact form saves `contact_messages`, emails the one support address with the sender as reply-to, and is answered from a console inbox (`contact.manage`), whose replies are emailed and kept; a hidden field drops bots, the route is rate limited, trackers never load on the form, and messages are deleted two years after they were last touched (spam after 30 days). Checkout no longer reports its result in a passing message: it always lands on `/dashboard/payments/:orderId`, which shows only what the API recorded (paid, confirming, failed, open, refunded) and polls while a webhook may still settle the payment. Retrying reopens the same Razorpay order, which accepts several attempts and captures at most one, so a retry cannot charge twice.

### ADR-039: Consent is a recorded tick; deleted accounts can be restored for 30 days (2026-10-07)
India's DPDP Act wants consent that is free, specific and given by a clear affirmative action, and the Consumer Protection (E-Commerce) Rules forbid recording a purchase consent from a pre-ticked box. Sign-up (including Google sign-up) and every purchase therefore need an unticked box the person ticks; the API refuses requests without it and records a `consents` row with the policy versions shown (the policy page's last change), so an edited policy is told apart from the one accepted. A new account through Google is created only from the sign-up page with the box ticked; from the sign-in page it is sent to sign up first. Deleting an account used to anonymize it at once, so a mistaken click was permanent. It now takes the owner's events offline and marks the account `PENDING_DELETION` for 30 days: every check that requires an `ACTIVE` account (sign-in, refresh, staff routes) already refuses it, the right password or Google offers a one-use restore token instead of a session, and restoring brings back exactly the events that went offline at the request time. After the window the worker sends a last email and erases the account; its events are purged with their photos, while orders, payments, consents and the audit log keep the bare account id because tax law and accountability require them. Requesting deletion needs the password (or a typed DELETE for Google-only accounts), and staff cannot reactivate such an account, so only the owner decides. The policies gained an account deletion page and a grievance redressal page with the timelines of the IT and e-commerce rules and the escalation routes (Grievance Appellate Committee, National Consumer Helpline, the Data Protection Board).

### ADR-040: Templates can be designed on a canvas; the artboard scales with CSS (2026-10-07)
Section templates compose a page from prebuilt layouts and a theme, so a designer could choose among variants but not place a photo in an arch beside a name, stack a countdown under a date pill or build the card-per-function invitations the market expects; each such idea meant a new React section. A `canvas` section instead stores a design: fixed artboards (phone, optionally desktop) with absolutely placed layers (text, image, shape, ornament, icon, widget), edited in the Studio with drag and drop. The design stays data in the same definition JSON, validated by the same schema and checked by the same matrix, licences and publishing flow, so the rule that templates are data holds. The renderer scales an artboard with CSS alone (percentage positions, `cqw` sizes, a container query choosing the artboard), so a composition keeps its proportions on every screen without measuring in the browser, server rendering and thumbnails stay static, and the phone frame in the Studio stays a phone; only shrinking long names runs in the browser. Colours are palette roles by default, so a canvas design restyles itself with the host's colour preset like every other template, and text is nudged to WCAG AA against the artboard's fill unless a designer opts a decorative layer out (the matrix then reports it). Layers never hold raw storage keys or URLs: image layers reference licensed assets that the definition lists in `assets` and browsers load through the public asset route, and host photos come through bindings. Widgets (countdown, directions, Google Calendar, RSVP scroll, detail rows) are drawn by the engine rather than as free HTML, so a design cannot carry script or arbitrary markup, and buttons open only `https:`, `mailto:`, `tel:` and same-page addresses. Films keep their own scene model; a canvas is a website section.

### ADR-041: Preview before paying: provisional accounts, preview links, the plan checked at publishing (2026-10-07)
The funnel lost most visitors at its first click: "Use this template" led to an email-and-password form, the chosen design was replaced by the free default when the event was created, a premium design could not even be saved without paying, and no page showed a draft to anyone. Hosts in India decide invitations with family on WhatsApp, so the product now gives them something to share first. The template page's quick start creates, in one request, a *provisional* account from a WhatsApp number alone (with the Terms box ticked, and updates on WhatsApp as a separate optional consent), a draft event with the chosen design and the type's functions, and a preview link, then signs the browser in; the link goes to the number on WhatsApp when the integration has a template for it. A provisional account is a real `users` row (`provisional = true`): every tenant route and the dashboard work for it, so the design and the functions are edited in the same place as for any host. What it cannot do is publish, pay, send invitations or add team members (`ACCOUNT_UNVERIFIED`), because those need an account someone can get back into and reach: securing it means a verified code on the number, an email and password, or Google. A number that already has an account is never a way into it: the quick start then requires the code, and codes travel only through the `whatsapp` queue as an approved authentication template. Template tiers are no longer enforced when a design is saved to a draft, only when the event is published; drafts and previews carry the watermark, so a host sees exactly what paying buys. The preview is a per-event unguessable token (`Event.previewToken`, replaceable) rather than a `?preview=1` flag on the public page, because the public page is gated by the access policy and a flag would open private events to anyone who learns the slug; the preview page is read-only, always watermarked and never indexed. The maintenance banner the audit flagged is the announcement setting in the console, not code.
